# 네이티브 액세스 토큰 인증

[문서 목차](../README.ko.md) · [English](../JWT_AUTH.md)

`HttpRoute.jwt_auth`는 운영자가 선택한 공개 키로 서명된 OAuth 액세스 토큰을 검증합니다. 로컬 JWKS 또는 고정된 HTTPS JWKS 엔드포인트/OIDC 검색으로 키를 가져올 수 있습니다. 구현된 토큰 프로필은 [RFC 9068](https://datatracker.ietf.org/doc/html/rfc9068)이며 검증은 [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)의 발급자, 대상, 알고리즘 및 토큰 유형 경계를 따릅니다. 여기서 OIDC 검색은 검증 키를 얻을 뿐 브라우저 authorization-code 흐름, 세션 발급, ID 토큰의 API 자격 증명 수락을 구현하지 않습니다.

```json
{
  "id": "orders-api",
  "hosts": ["api.example.test", "www.api.example.test"],
  "path_prefix": "/orders",
  "path_match": "segment_prefix",
  "access_mode": "protected",
  "require_tls": true,
  "backends": ["http://127.0.0.1:8080"],
  "jwt_auth": {
    "verification": {
      "issuer": "https://identity.example.test/",
      "audiences": ["orders-api"],
      "profile": "rfc9068",
      "algorithms": ["RS256"],
      "leeway_seconds": 0,
      "max_lifetime_seconds": 3600,
      "scope_claim": "scope",
      "groups_claim": "groups",
      "required_scopes": ["orders:read"],
      "required_groups": []
    },
    "keys": {
      "source": "remote",
      "config": {
        "endpoint": {"kind": "oidc"},
        "cache_ttl_seconds": 300,
        "refresh_cooldown_seconds": 10,
        "timeout_ms": 3000
      }
    },
    "hide_credentials": true,
    "identity_header": "x-verified-subject"
  },
  "resource_policy": {
    "resource_id": "orders",
    "principal": {"source": "jwt"},
    "allow": [{"subjects": ["service-reader"], "methods": ["GET", "HEAD"]}]
  }
}
```

예시에는 이 액세스 토큰 프로필을 실제로 발급하고 신뢰된 인증서와 검색으로 게시된 서명 키를 가진 소유 발급자가 필요합니다. 토큰이나 서명 비밀은 포함하지 않습니다. `jwt_auth`는 선택된 경로를 인증합니다. 대체 공개 경로로부터 호스트/경로 네임스페이스도 보호하려면 표시된 대로 [resource_policy](RESOURCE_POLICY.md)를 추가하십시오. `hosts`의 도메인 별칭은 정책을 공유합니다.

## 검증 계약

정확히 하나의 `Authorization: Bearer <compact-JWS>` 필드만 받습니다. 쿼리 매개변수, 쿠키, 프록시 인증 및 다른 헤더는 대체 자격 증명 원본이 아닙니다. 누락/잘못된 형식/중복 인증, 잘못된 서명, 알 수 없는 키, 잘못된 발급자/대상/유형과 잘못된 클레임은 Bearer 챌린지와 401을 반환합니다. 필요한 scope/group이 없는 유효 토큰은 403을 반환합니다. 리소스 주체/메서드 거부는 별도의 403 결정입니다. 원격 키를 사용할 수 없거나 키 상태가 만료되었거나 암호 작업 승인이 소진되면 인증 없이 전달하지 않고 503을 반환합니다.

보호된 JOSE 헤더에는 `alg`, `kid`, `typ`만 있습니다. 토큰 유형은 ASCII 대소문자 구분 없이 `at+jwt`, `application/at+jwt`를 허용합니다. 일반 `JWT`, ID 토큰, 비보안 `none`, HMAC 알고리즘, 토큰 제공 키 URL/키, critical extension, 압축, 분리/비인코딩 payload는 거부합니다. 헤더/클레임/JWKS JSON 멤버 중복은 map이 가리기 전에 거부합니다. bearer는 16 KiB, 디코드 JOSE 헤더는 2 KiB, 디코드 클레임은 8 KiB로 제한하며 정규 unpadded base64url 인코딩을 사용합니다.

RS256, PS256, ES256(P-256), EdDSA(Ed25519)를 개별 허용 목록으로 사용합니다. 각 사용 가능 키는 하나의 알고리즘과 정확한 하나의 `kid`에 바인딩됩니다. JWK `alg`가 없으면 키 유형과 호환되는 구성 알고리즘이 정확히 하나일 때만 허용합니다. RSA/HMAC 알고리즘 변환은 없습니다. RSA 모듈러스는 2048–4096비트, 지수는 65537입니다. 암호화는 준비 중 공개 키 검증을 포함한 RustCrypto 제공자의 `jsonwebtoken`을 사용합니다. 사용자 정의 서명 알고리즘은 구현하지 않습니다. 라이브러리 검증은 요청마다 준비된 키 자료로 crypto verifier를 만들며 공유 Send/Sync verifier는 해당 API가 노출하지 않습니다.

필수 클레임은 `iss`, `aud`, `sub`, `exp`, `iat`, `client_id`, `jti`입니다. 발급자는 구성 HTTPS issuer와 정확히 비교하며 토큰 대상 중 하나는 구성 대상과 정확히 일치해야 합니다. 날짜는 부호 없는 정수 초이며 만료는 발급 뒤이고 구성 최대 수명 안이어야 합니다. `nbf`는 있으면 검사합니다. leeway는 명시적이고 기본 0, 최대 60초입니다. 만료/발급/not-before는 블로킹 암호 작업 후 인증 결과를 승인하기 직전에 다시 검사합니다. `jti`는 필수지만 재생 감지를 제공하지 않습니다.

scope는 공백 구분 문자열, group은 문자열 배열입니다. 구성 클레임 이름은 JSON 경로가 아닌 리터럴 최상위 멤버를 선택합니다. 요구 scope와 group은 모두 일치해야 하며 값은 정확하고 대소문자를 구분합니다. 선택 scope/group 클레임 누락은 빈 집합을 만들고, 잘못되었거나 중복/과대 속성은 토큰을 무효화합니다. scope 토큰은 출력 가능한 OAuth scope 문자, group은 제한된 UTF-8 문자열을 사용합니다. 클라이언트 헤더나 Lua는 이 검증 속성을 제공할 수 없습니다.

현재 제한은 구성 대상 최대 8개, 토큰 대상 16개, 토큰 또는 요구 목록당 scope/group 32개, 속성당 128바이트, subject/audience/client ID/JTI당 255바이트입니다. issuer는 최대 512바이트입니다. 클레임 이름은 등록된 신원/시간 클레임을 제외한 서로 다른 제한 ASCII 이름입니다. 구성당 서로 다른 JWT 경로 정책은 최대 64개를 준비하며 동일 정책은 별칭과 변경 없는 스냅샷에서 런타임을 공유합니다.

## 공개 키 원본과 회전

로컬 키에는 `"keys":{"source":"local","jwks":{"keys":[...]}}`를 사용하십시오. 이 문서에는 공개 JWK 자료만 허용되며 개인/대칭 키 자료는 거부됩니다. 로컬 JWKS는 게시 전에 검증합니다. 다른 알고리즘이나 암호화 용도의 제한된 공개 키를 포함할 수 있지만 호환되는 구성 검증 키만 승인합니다. 중복 `kid`는 전역으로 거부하고 사용 가능한 서명 키가 하나 이상 남아야 합니다. 선택된 서명 키는 선언된 용도를 포함해 검증합니다. JWKS 문서는 128 KiB, 총 32개 항목으로 제한됩니다.

원격 원본 구성은 `endpoint:{"kind":"oidc"}` 또는 `endpoint:{"kind":"jwks","url":"https://keys.example.test/jwks"}`를 사용합니다. 검색은 구성 issuer에서 파생되며 반환 issuer는 정확히 일치해야 합니다. 이 구현에서 검색된 JWKS URL은 같은 HTTPS origin이어야 하며 다른 origin을 신뢰하려면 JWKS 엔드포인트를 명시적으로 고정하십시오. [OIDC Discovery](https://openid.net/specs/openid-connect-discovery-1_0.html)는 issuer/metadata 검증을 정의하며 same-origin 규칙은 이 배포의 추가 제한입니다.

HTTP 클라이언트는 TLS를 검증하고 환경 프록시와 리디렉션을 비활성화하며 키 엔드포인트에 클라이언트 Bearer 자격 증명을 보내지 않습니다. URL에는 자격 증명, 쿼리, 프래그먼트가 있을 수 없습니다. 선택 `ca_pem`은 비공개 IdP의 공개 PEM 신뢰 앵커를 추가하며 비보안 TLS 옵션은 없습니다. 1–5000ms의 하나의 타임아웃이 검색과 JWKS 검색을 함께 제한하고 응답 본문은 스트리밍 중 제한됩니다.

원격 구성 검증은 네트워크에 접근하지 않습니다. 최초 사용이 키 캐시를 지연 초기화합니다. 콜드 또는 만료 캐시는 issuer를 사용할 수 없으면 fail closed하며 하나의 요청이 키를 가져오는 동안 동시 콜드 요청은 503을 받을 수 있습니다. 알 수 없는 키 ID는 요청 클라이언트가 취소해도 네트워크 I/O 전에 예약한 cooldown의 적용을 받는 하나의 제한된 새로 고침만 유발합니다. 무제한 대기열은 없습니다. 인증 세션이 존재하는 동안 제한된 공유 monitor가 런타임 키 캐시를 새로 고치며 세션 종료 후 유휴 fetch는 하지 않습니다.

TTL 절반 이후 알려진 키 요청이나 공유 세션 monitor가 cooldown에 따라 새로 고칠 수 있습니다. 동시 요청은 여전히 신선한 키를 사용합니다. 새로 고침에 실패하면 유발 요청은 원래 마감 전의 키만 사용할 수 있으며 알 수 없거나 만료 키에는 대체가 없습니다. 조기 새로 고침 창을 위해 cooldown을 TTL보다 짧게 선택하십시오.

하드 캐시 TTL은 1–3600초로 구성하고 fetch 시작에서 측정합니다. 지연 응답은 연장할 수 없습니다. 최종 키 신원/마감 fence는 캐시 키 세대가 바뀐 후 제거/만료 전에 선택한 키가 작업을 승인하지 못하게 합니다. 변경 없는 공개 JWK는 성공 새로 고침에서 키 신원을 유지하고 제거/변경 키는 무효화됩니다. 새로 고침 오류는 이전 마감을 연장하지 않습니다. 캐시된 알려진 키는 그 마감까지 만 권위 있으므로 issuer 장애가 즉시 신선한 캐시를 무효화하지는 않습니다. 유효한 원격 빈 JWKS 또는 사용 가능 서명 키가 없는 구조 유효 집합은 캐시 키를 명시적으로 철회합니다. 잘못된 문서는 새로 고침 실패일 뿐 철회 세대를 만들지 않습니다. 로컬 JWKS는 계속 적격 키가 필요합니다. 철회된 키를 복구하면 새 신원을 만들고 오래된 세션을 되살릴 수 없습니다.

JWT 정책, issuer, audiences, 원본, 신뢰 설정 변경은 새 런타임 세대를 만들고 관련 없는 경로 업데이트는 기존 런타임/캐시를 유지합니다. 승인된 JWT 요청도 전체 선택 경로 세대를 유지합니다. 같은 경로(백엔드/일치 필드 포함) 편집, 비활성화/제거, 토큰 시간 무효화, 서명 키 철회는 업로드, 응답 본문, SSE, WebSocket 터널을 종료합니다. 변경 없는 경로는 같은 HTTP/2 연결에 다중화된 다른 경로를 포함해 리스를 보존합니다.

리스는 원시 bearer 문자열이 아닌 검증 토큰 클레임과 선택 키 신원을 사용합니다. 시간 유효성에는 구성 leeway와 벽시계/단조 만료 마감이 포함됩니다. 프레임별 동기 검사는 서명 검증이나 네트워크 요청을 하지 않고 250ms 타이머도 유휴 본문/터널을 깨웁니다. 외부 인증, Lua 평가, 본문 변환 버퍼링, origin 헤더 대기도 리스 종료와 경쟁합니다. 응답 헤더 전 종료는 업스트림 실패나 다른 백엔드 재시도로 취급하지 않고 503을 반환합니다. 이 간격은 스케줄러 가용성에 의존하며 즉시 전 플릿 철회를 보장하지 않습니다. 이미 전달한 바이트는 회수할 수 없습니다.

원격 키 제거는 성공 새로 고침 또는 캐시 하드 마감으로 관측되며 실패 새로 고침은 마감을 연장하지 않습니다. TTL과 cooldown에는 네트워크 지연과 새로 고침을 위한 여유를 두십시오. 예를 들어 cooldown이 TTL과 같으면 하드 만료 전 새로 고침을 막아 유효 세션을 종료할 수 있습니다. monitor는 런타임별 작업을 공유하고 스트림마다 fetch loop를 만들지 않습니다. JWT와 워크로드 mTLS 리스는 조합되며 둘 중 하나의 만료/철회가 스트림을 끝낼 수 있습니다. 아래 구성 토큰 ID 거부 목록은 운영자 관리 철회를 추가하며 온라인 introspection, 즉시 issuer logout, 분산 철회 권한은 별도 요구 사항입니다.

## 운영자 관리 토큰 철회

`jwt_auth.verification.revocation`은 경로 범위 승인 조건을 추가합니다:

```json
{
  "issued_before": 1789257600,
  "token_ids": ["withdrawn-token-id"]
}
```

게이트웨이는 서명된 `jti`가 목록 ID와 정확히 일치하거나 서명된 `iat`가 `issued_before`보다 엄격히 이전이면 암호학적으로 유효한 토큰도 401로 거부합니다. cutoff와 같은 값은 유효하며 구성 time leeway는 철회를 완화하지 않습니다. 생략/null revocation은 기존 동작을 유지합니다. 생략/null cutoff와 빈 목록은 추가 조건을 부과하지 않습니다. cutoff는 0–253402300799 UNIX 초 정수이고 목록은 앞뒤 공백/제어 문자가 없는 1–255 UTF-8 바이트의 고유 ID 최대 1,024개를 받습니다. 검증 오류는 토큰 ID를 되돌려 주지 않습니다. 조회는 서명/클레임 검증 후 준비된 hash set을 사용하고 새 issuer 요청은 없습니다.

영어/한국어 HTTP 경로 편집기는 두 필드를 노출합니다. 기존 리비전 검사 경로 또는 전체 문서 구성 API로 게시하십시오. 영구 구성에는 식별자만 있고 필수 bearer 자격 증명은 없으므로 운영자는 서명 토큰이 아니라 `jti`만 입력해야 합니다. 공유 리소스 별칭은 한 별칭이 철회 조건을 생략하지 못하도록 완전한 JWT 검증 정책이 같아야 합니다. 관련 없는 issuer/경로는 독립적입니다.

성공한 로컬 게시는 변경된 경로에서 허용 목록에 없는 토큰을 포함한 **모든 승인 스트림을 종료**합니다. 전체 경로 정책 세대가 변경되기 때문입니다. 다른 유효 토큰 클라이언트는 새 검증기가 서명 키를 얻으면 재연결할 수 있습니다. 다른 JWT 정책 편집처럼 철회 편집은 새 런타임/캐시를 만들며 원격 키 경로는 새 성공 JWKS fetch가 필요할 수 있고 없으면 fail closed합니다. 변경 없는 관련 없는 경로는 스트림을 보존합니다. 항목 제거에도 보수적 동작이 적용됩니다. 철회 항목은 자동 만료/삭제되지 않으므로 leeway를 포함해 영향 토큰이 더는 유효하지 않을 때까지 보존하십시오. 항목을 명시적으로 제거하거나 cutoff를 낮추면 만료되지 않은 토큰을 다시 허용할 수 있지만 이미 닫힌 스트림을 재개할 수는 없습니다.

이는 영구 구성 정책이며 issuer introspection 서비스나 자동 동기화 logout feed가 아닙니다. 공유 저장소 쓰기는 모든 데이터 플레인 리더가 활성화했다는 증거가 아닙니다. 다중 노드 전파, 승인, 권한 fencing, 영구 행위자 감사에는 기존 제한이 남습니다. 이 기능은 선택적 연결 인덱싱이나 플릿 전체 즉시 철회 마감을 주장하지 않습니다.

## 요청 처리, 관측성 및 UI

JWT와 네이티브 Basic은 모두 Authorization을 소비하므로 같은 경로에서 공유할 수 없습니다. JWT 뒤에 추가 외부 인가 검사가 올 수 있습니다. 외부 서비스는 요청 헤더에 명시적으로 포함한 경우에만 원래 bearer를 받습니다. 기본 `hide_credentials:true`는 해당 검사 뒤 Lua/업스트림 전달 전에 원래 bearer를 제거합니다. 구성된 모든 인증 검사는 성공해야 하고 리소스 정책 종결 응답 제한은 계속 적용됩니다.

선택 신원 헤더는 검증된 subject를 전달합니다. 클라이언트 복사본은 검증 전에 제거되고 외부 auth는 같은 헤더를 주장할 수 없으며 네이티브 변환도 이를 수정할 수 없습니다. 런타임 신원 재주장과 Lua 변경 제한이 수립된 값을 보호합니다. 일반 Lua 애플리케이션 변환은 계속 지원합니다. JWT 경로는 레거시 분류 JWT 경로를 포함해 공유 응답 캐시를 우회하고 캐시 전용 요청도 만족 불가 504 전에 인증합니다.

서명 검증은 사용 가능한 CPU의 두 배(최소 2, 최대 64) 크기의 프로세스 전체 fail-fast semaphore로 비동기 I/O 워커 밖에서 실행합니다. 요청 클라이언트가 연결을 끊어도 blocking task는 permit을 유지합니다. 무제한 crypto queue는 없습니다. Prometheus와 상태는 `jwt_auth_rejections_total`, `jwt_auth_unavailable_total`, `jwt_auth_capacity_rejections_total`을 노출합니다. `jwt_lease_terminations_total`은 토큰 시간, 키, 경로 세대 무효화로 인한 승인 요청/본문/터널 가드 종료를 세며 고유 사용자나 연결 수가 아닙니다. 이는 운영 카운터이지 영구 보안 감사나 사용자별 결정 로그가 아닙니다. 실패 응답은 토큰과 원시 검증 오류를 반환하지 않습니다.

HTTP 편집기는 전용 영어/한국어 JWT 검증, 키 원본, 클레임, 자격 증명, 신원 제어 및 리소스 정책의 JWT 주체 옵션을 제공합니다. 기존 경로/전체 문서 API와 리비전 검사는 이 필드를 전달합니다. 공유 구성에 게시하기 전에 모든 리더를 업그레이드하십시오. 이전 바이너리는 알 수 없는 필드를 거부합니다. 롤백은 이전 바이너리를 로드하려고 필드를 제거하지 말고 인증 경계를 보존해야 합니다.
