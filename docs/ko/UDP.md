# UDP 라우팅과 QUIC 패스스루

[문서 목차](../README.ko.md) · [English](../UDP.md)

Hangang은 UDP 데이터그램을 설정된 백엔드로 중계하며, 유휴 시간 제한이 지나거나 경로가 변경될 때까지 각 클라이언트 플로를 같은 백엔드에 유지합니다. 같은 중계기는 QUIC 백엔드가 제공하는 HTTP/3를 포함한 암호화 QUIC도 전달할 수 있습니다. Hangang은 QUIC를 종료하지 않으며, 암호화된 내용에 HTTP 경로, Lua, JWT 또는 본문 변환 정책을 적용하지 않습니다.

## 구성

로컬 JSON 구성에 `udp` 배열을 추가하십시오. 아래 조각은 루프백 UDP 포트에서 수신하고 두 개의 리터럴 백엔드 주소로 전달합니다.

```json
{
  "udp": [{
    "id": "quic-edge",
    "enabled": true,
    "protocol": "quic",
    "listen": "127.0.0.1:8443",
    "backends": ["127.0.0.1:9443", "127.0.0.1:9444"],
    "idle_timeout_ms": 30000,
    "max_sessions": 1024,
    "max_datagram_bytes": 65507
  }]
}
```

일반 데이터그램에는 `protocol: "udp"`를 사용하십시오. `quic`은 의도된 용도를 나타내며 최소 1,200바이트의 데이터그램 허용량이 필요하지만, 패킷을 검사하거나 분류하지는 않습니다. [완전한 UDP 예제](../../examples/udp/config.json)는 별도로 프로비저닝한 백엔드를 시작하기 전에 `hangang --config examples/udp/config.json --check`로 검증할 수 있습니다.

| 필드 | 기본값 | 유효 범위 또는 동작 |
| --- | --- | --- |
| `id` | 필수 | ASCII 문자, 숫자, 점, 밑줄 또는 대시 1~64자이며 HTTP/TCP/UDP 경로 ID 전체에서 고유해야 합니다. |
| `enabled` | `true` | 비활성 경로는 구성을 유지하지만 활성 UDP 리스너가 없습니다. |
| `listen` | 필수 | 0이 아닌 포트를 가진 리터럴 IPv4 또는 대괄호로 감싼 IPv6 소켓 주소입니다. 와일드카드 바인드를 지원합니다. |
| `backends` | 필수 | 서로 다른 유니캐스트 리터럴 소켓 주소 1~64개입니다. DNS 조회, 멀티캐스트, 브로드캐스트, 미지정 대상은 허용되지 않습니다. |
| `protocol` | `udp` | `udp` 또는 불투명한 `quic` 패스스루입니다. |
| `idle_timeout_ms` | `30000` | 성공적으로 전달된 애플리케이션 데이터그램이 없는 시간 기준 100~86,400,000ms입니다. |
| `max_sessions` | `1024` | 1~16,384이며, 구성된 경로 전체의 합은 16,384를 넘을 수 없습니다. |
| `max_datagram_bytes` | `65507` | 1~65,507바이트이며, `quic`에는 최소 1,200바이트가 필요합니다. 너무 큰 패킷은 잘라 전달하지 않고 폐기합니다. |

UDP 경로는 전체 1,024개 경로 구성 한도 안에서 최대 64개까지 허용됩니다. TCP와 UDP는 전송 계층이 다르므로 같은 숫자 포트를 사용할 수 있습니다. 충돌하는 UDP 바인드는 후보 준비를 실패시킵니다. 백엔드는 게이트웨이에서 도달 가능해야 하며, 경로 구성만으로 서비스가 만들어지지는 않습니다.

## 플로 어피니티와 리소스 한도

플로 키는 하나의 리스너 안에서 클라이언트 IP와 소스 포트입니다. 새 플로는 라운드 로빈으로 백엔드를 선택합니다. 각 플로는 연결된 업스트림 UDP 소켓을 가지며, 선택한 엔드포인트의 응답만 받습니다. 서로 다른 클라이언트 플로는 업스트림 소켓을 공유하지 않습니다. 백엔드 애플리케이션에는 게이트웨이의 소스 주소가 보입니다. 네트워크가 직접 반환과 소스 IP 보존을 위해 설계되었다면 별도의 [DSR 동반 구성 요소](../DSR.md)를 사용하십시오.

UDP는 빈 페이로드를 포함해 데이터그램 경계를 보존하지만 신뢰성, 순서, 재시도 또는 백엔드 상태 점검을 추가하지 않습니다. 잃은 패킷은 그대로 잃으며 재전송은 애플리케이션이나 QUIC 엔드포인트의 책임입니다. 백엔드 선택은 플로에 고정되고 다른 대상으로 재시도하지 않습니다.

각 세션에는 최대 8개 발신 패킷의 큐가 있습니다. 프로세스 전체 64MiB 예산은 대기 중인 페이로드 바이트와 세션별 수신 버퍼를 제한합니다. 리스너 버퍼, 소켓/커널 메모리, 작업 메타데이터, 구성은 별도입니다. 세션 한도와 바이트 한도는 독립적이므로, 큰 데이터그램 한도는 `max_sessions`보다 먼저 메모리 수용량을 소진할 수 있습니다. 수용량이 포화되거나 큐가 가득 차면 데이터그램을 폐기합니다. UDP 서비스에 알맞은 방화벽/소스 제한을 구성하십시오. QUIC/백엔드 인증은 계속 백엔드의 책임입니다.

## 다시 불러오기, 활성화, 종료

UDP는 게이트웨이의 리비전 검사 전체 구성 준비에 참여합니다. 새 소켓은 게시 전에 바인드됩니다. 준비에 실패하면 활성 구성과 리스너는 그대로 유지됩니다. 관계없는 HTTP/구성 편집은 변경되지 않은 UDP 플로를 보존합니다.

수신 주소가 같더라도 UDP 경로를 변경하면 기존 세션은 퇴역합니다. 경로를 비활성화하거나 제거하면 해당 리스너와 세션이 닫힙니다. 이 변경 뒤 클라이언트는 다시 연결해야 합니다. 전환 중 도착한 데이터그램은 폐기될 수 있고 이미 전달된 바이트는 회수할 수 없습니다. 리스너 세대가 교체되면 카운터가 다시 시작됩니다. 프로세스 종료는 TCP 연결 드레인 프로토콜을 적용하지 않고 UDP 세션을 닫습니다.

이 릴리스는 **로컬 파일 구성 권한 저장소에서만** UDP를 지원합니다. 공유 저장소, Kubernetes 컨트롤러 모드, `--supervised` 모드는 UDP 경로를 거부합니다. UDP 소켓/세션 핸드오프는 구현되지 않았습니다. 문서화된 [HTTP/TCP 감독 연속성](../UPDATES.md)을 UDP/QUIC 업그레이드 연속성으로 해석해서는 안 됩니다. 읽기 전용 컨테이너 교체도 UDP 세션을 재설정합니다.

## 향후 연속성 작업

감독 프로세스 교체를 넘는 UDP/QUIC 연속성은 v0.2.0 구현 범위 밖의 향후 작업으로 기록되어 있습니다. 향후 구현에는 리스너 소유권 이전과 백엔드 어피니티 및 업스트림 소켓 매핑의 보존이 필요하며, 성공적인 교체와 실패한 후보 롤백 모두에서 활성 UDP와 QUIC 연결로 검증해야 합니다. 그때까지 유지 보수를 계획할 때는 위에서 설명한 재시작 및 플로 재설정 동작을 사용하십시오.

## QUIC 경계

QUIC 엔드포인트는 TLS, 인증서, 연결 ID, 혼잡 제어, 손실 복구 및 HTTP/3를 처리합니다. Hangang은 암호화된 데이터그램을 변경하지 않고 전달합니다. 안정적인 클라이언트 IP/포트는 QUIC가 연결 ID나 키를 바꿔도 선택된 백엔드를 유지합니다. 클라이언트 주소 마이그레이션이나 NAT 재바인딩은 새 중계 플로를 만들며 다른 백엔드를 선택할 수 있습니다. 연결 ID 인식 라우팅은 구현되지 않았습니다. 유휴 만료도 기존 업스트림 매핑을 잃게 합니다. 엔드포인트의 keepalive/유휴 정책을 고려하여 중계 유휴 예산을 선택하십시오.

네트워크 주소로 라우팅할 때의 QUIC 영향은 [RFC 9000의 단순 로드 밸런서](https://www.rfc-editor.org/rfc/rfc9000.html#section-5.2.3)를 참조하십시오. `quic` 모드는 SNI 라우팅, HTTP/3 종료, QUIC 인식 상태 점검 또는 DSR을 제공하지 않습니다.

## 관리와 관측

영문/한국어 **UDP / QUIC** 콘솔 페이지는 `GET /v1/config` 및 리비전 검사 `PUT /v1/config`를 통해 중계기를 생성, 편집, 삭제, 토글합니다. 편집은 관계없는 구성을 보존하고 충돌하는 중계기 변경을 거부합니다. 별도의 UDP 경로 CRUD 엔드포인트는 없으며 [OpenAPI 스키마](../openapi.json)가 `UdpRoute`를 정의합니다.

`GET /v1/status`와 상태 SSE 이벤트에는 `udp_routes`(구성된 모든 경로)와 `udp.routes`(활성 리스너만)가 포함됩니다. 각 활성 항목은 ID, 프로토콜, 주소, 활성 세션, 세션 한도, 백엔드 수, 데이터그램 카운터를 보고합니다. `datagrams_forwarded`와 `responses_forwarded`는 확인된 전달이 아니라 성공한 로컬 소켓 전송을 셉니다. `dropped_datagrams`는 관찰된 중계 거부/실패를 셉니다. 커널 폐기는 이 카운터로 완전히 관측할 수 없습니다. 이 관측값은 영속 로그나 패킷 캡처가 아닙니다.

Prometheus `/metrics`는 `hangang_udp_sessions` 및 `hangang_udp_datagrams_received_total`, `hangang_udp_datagrams_forwarded_total`, `hangang_udp_responses_forwarded_total`, `hangang_udp_dropped_datagrams_total`, `hangang_udp_sessions_created_total` 카운터를 내보내며, 모두 `route` 레이블을 가집니다. 이들은 같은 활성 리스너 범위를 사용하고 해당 리스너 세대가 바뀌면 재설정됩니다.

Docker에서는 예를 들어 `"8443:8443/udp"`처럼 UDP 포트를 명시적으로 게시하고 컨테이너 인터페이스에서 수신하십시오. 기본 [Compose 템플릿](../DEPLOYMENT.md)은 문서화한 TCP 포트만 게시합니다. 콘솔에서 경로를 추가해도 Docker 포트 매핑은 바뀌지 않습니다.

## 검증

```sh
cargo test --locked --lib udp::tests
cargo test --locked --test udp_lifecycle
cargo build --locked --bin hangang
python3 tests/udp_smoke.py
make static
python3 tests/datagram_container.py
```

OpenAPI 계약 검사는 `jsonschema`가 설치된 Python 환경에서 `python3 tests/udp_schema.py`를 실행하십시오.

컨테이너 픽스처는 고정된 aioquic 테스트 피어를 빌드하고 게시 포트가 없는 소유 내부 Docker 네트워크를 만듭니다. UDP 플로 격리, 균형 조정, 경계, 구성 거부/활성화 및 암호화 QUIC 패스스루를 통한 실제 TLS 검증 HTTP/3를 확인합니다. CID 순환은 클라이언트 튜플을 바꾸지 않고 실행하며, 이는 마이그레이션 테스트가 아닙니다. 빌드 종속성에는 네트워크 접근이 필요하지만 프로토콜 트래픽은 소유 테스트 네트워크 내부에 머뭅니다. 실행기에는 로컬 Docker 데몬, Python/pip, OpenSSL이 필요하며 종료 시 컨테이너와 네트워크를 제거합니다. 이는 정확성 테스트이며 처리량 순위나 가용성 보장이 아닙니다.
