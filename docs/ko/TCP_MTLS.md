# 수신 상호 TLS를 사용하는 인증된 TCP

[문서 목차](../README.ko.md) · [English](../TCP_MTLS.md)

`TcpRoute.inbound_tls`는 Hangang에서 클라이언트 TLS를 종료하고 업스트림을 선택하거나 연결하기 전에 정확한 워크로드 URI를 인가합니다. 업스트림은 복호화된 애플리케이션 바이트 스트림을 받습니다. 해당 홉에도 암호화가 필요하면 업스트림 TLS를 별도로 구성하십시오. 이 기능은 불투명 프로토콜에 바이트나 HTTP 신원 헤더를 추가하지 않습니다.

```json
{
  "tcp": [{
    "id": "workload-database",
    "listen": "0.0.0.0:9443",
    "backends": ["127.0.0.1:5432"],
    "inbound_tls": {
      "cert_file": "/etc/hangang/workload/server.pem",
      "key_file": "/etc/hangang/workload/server-key.pem",
      "client_ca_file": "/etc/hangang/workload/client-ca.pem",
      "client_crl_file": "/etc/hangang/workload/client.crl.pem",
      "allowed_uri_sans": ["spiffe://example.test/services/orders"],
      "handshake_timeout_ms": 5000
    }
  }]
}
```

파일 경로는 정규화된 절대 경로여야 하며 게이트웨이 호스트가 관리하는 자료를 가리켜야 합니다. 예시에는 인증서나 개인 키가 없으므로 파일이 존재하기 전에는 시작할 수 없습니다. 편집기는 개인 PEM 텍스트가 아니라 경로를 받습니다. 서로 다른 클라이언트가 같은 인가된 워크로드 신원에 대해 다른 인증서를 사용할 수 있습니다. 이것은 서비스 신원이지 개별 인간 행위자의 증거가 아닙니다.

## 인증 및 인가

TLS 핸드셰이크는 rustls의 필수 [WebPkiClientVerifier](https://docs.rs/rustls/latest/rustls/server/struct.WebPkiClientVerifier.html), 명시적 클라이언트 CA 루트, 인증서 유효성 및 클라이언트 인증 검증을 사용합니다. 시스템/web PKI 루트는 암묵적으로 신뢰되지 않습니다. 인증서 누락, 신뢰되지 않는 발급자, 잘못된 서명, 만료된 인증서는 업스트림에 도달할 수 없습니다. 새 인증서 검사 없이 재개 세션이 승인되는 것을 피하기 위해 이 리스너에서 TLS 세션 재개, 티켓 및 early data를 비활성화합니다.

TLS 인증 성공 후 리프에는 URI subject alternative name이 정확히 하나 있어야 하며, 그 URI는 `allowed_uri_sans` 항목과 정확히 일치해야 합니다. DNS 이름, common name, 클라이언트 제공 HTTP 헤더 및 SNI는 워크로드 신원 근거가 아닙니다. CA가 유효하지만 목록에 없는 신원은 거부됩니다. 허용 네임스페이스는 엄격한 SPIFFE URI 형식입니다. [SPIFFE 개념](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/)을 참조하십시오. 이는 SPIRE 에이전트, 워크로드 증명 구현 또는 완전한 X.509-SVID 적합성 주장이 아닙니다.

허용 목록은 최대 2,048바이트의 서로 다른 URI 1–128개입니다. 와일드카드나 regex 인가는 사용하지 않습니다. 신뢰 도메인 이름은 소문자여야 하며 자격 증명, 포트, 쿼리/프래그먼트, 퍼센트 이스케이프, 점 세그먼트 및 모호한 경로는 거부됩니다. 핸드셰이크 타임아웃은 1–10,000ms(기본 5,000)이며 기존 전역 및 경로 연결 허가를 유지합니다. 프로세스 전체 fail-fast 게이트는 동시 워크로드 핸드셰이크를 사용 가능한 CPU의 두 배(최소 2, 최대 64)로 제한하며 대기열은 없습니다. 한 구성에는 서로 다른 수신 정책이 최대 64개 있을 수 있습니다. 자료는 파일별로 제한되며 구성 게시 중 동일한 정책마다 한 번 준비되고 연결마다 읽지 않습니다.

## 리스너 분리와 변경

수신 종료와 `sni` 패스스루는 한 경로에서 공존할 수 없습니다. 종료 리스너는 패스스루나 평문 경로와 공유할 수 없습니다. `inbound_tls`가 없거나 null이면 기존 일반 TCP 및 패스스루 경로는 동작을 유지합니다.

활성 mTLS 리스너는 경로 이름 변경을 통해서도 같은 주소의 활성 비인증 경로로 직접 교체할 수 없습니다. 먼저 이전 리비전에서 제거 또는 비활성 상태를 게시한 뒤 소켓 용도를 바꾸십시오. UI는 일반 경로 활성화를 인증 설정과 별도로 노출합니다.

구성 준비는 TCP 경로와 mTLS 정책 형태를 검증합니다. 활성 수신 mTLS 바인딩은 게시 후 로컬 인증서, 키, 신뢰 루트, CRL 파일을 확인합니다. 메타데이터는 500ms마다 폴링하고 전체 내용은 5초마다 확인하며, 경로가 변하지 않은 변경도 포함합니다. 새 바인딩은 게시 후 자료 검증이 성공할 때까지 사용할 수 없습니다. 변경되거나 잘못된 클라이언트 CA 또는 CRL은 이전 신뢰를 대체 수단으로 유지하지 않고 해당 바인딩의 승인과 기존 인증 스트림을 닫습니다. 검증된 교체는 새 자료 세대를 만듭니다. 비활성 경로는 구조 검증은 유지하지만 개인 자료는 읽지 않으므로 손상되거나 없는 파일이 리스너 비활성화를 막지 않습니다.

감시기는 전송 역할별로 동일한 정책을 그룹화하므로 여러 바인딩이 한 검사에서 같은 자료를 독립적으로 다시 열고 구문 분석하지 않습니다. 이 폴링 간격은 스케줄링 목표이며 파일 시스템 지연, 검사 크기 및 스케줄러 부하가 관측 지연에 영향을 줍니다. 감독형 핸드오프 후 이전 프로세스가 수립된 워크로드 연결을 배출하는 동안에도 자료 검사는 계속됩니다. 로컬 파일 새로 고침은 플릿 전체 철회 순서나 CRL 롤백 방지를 강제하지 않습니다.

`GET /v1/status`는 각 **활성** 수신 mTLS 경로를 `workload_materials[{kind:"tcp",id,ready}]`로 보고합니다. `ready:false`는 이 인스턴스가 현재 해당 바인딩의 인증된 승인을 거부함을 뜻합니다. TCP 경로 인벤토리는 이 로컬 런타임 상태를 표시하며, 응답 없음, 미게시 초안 또는 리비전 불일치는 unknown으로 표시합니다. 상태에는 파일 경로나 인증서 내용이 없으며 플릿 전체 준비 상태나 자료 배포를 수립하지 않습니다. 시작 시 구성된 워크로드 바인딩을 최대 10초 기다립니다. 이후 로컬 자료 실패가 전역 `/healthz` 준비 상태를 반드시 끄지는 않습니다. 다른 리스너가 계속 제공할 수 있으므로 바인딩별 상태나 자료 게이지를 확인하십시오.

핸드셰이크 후와 아웃바운드 다이얼 후에 연결은 준비된 세대가 여전히 활성인지 검사합니다. 수립된 인증 연결은 250ms마다 세대/신원 유효성을 검사하고 경로가 제거, 비활성화, 이동되거나 보안 자료/정책이 교체되면 닫습니다. 애플리케이션 데이터는 새 주체로 재해석되지 않습니다. 이 간격은 동작하는 런타임에서의 스케줄링 경계이지 실시간 운영체제 보장이 아닙니다. 이미 전달된 바이트는 회수할 수 없습니다. 백엔드 변경만으로는 기존 멤버 수명 주기 규칙을 따릅니다.

## 철회 및 관측성

`client_crl_file`이 설정되면 최대 16개 CRL을 허용합니다. 준비에는 thisUpdate ≤ 현재 시간 < nextUpdate가 필요하며, rustls는 핸드셰이크 중 알 수 없는 철회 상태, 잘못된 CRL 서명 및 만료된 CRL을 거부합니다. 제시된 체인에 필요한 CRL을 제공하십시오. 생략하면 CRL 기반 철회 검사가 없고 인증서 만료 및 명시적 구성/정책 철회는 계속 적용됩니다. OCSP나 자동 CRL 다운로드는 없습니다. 신원 리스 만료는 제시된 인증서 체인과 구성된 CRL 유효성으로 제한됩니다. 단조 마감 시간은 벽시계가 뒤로 바뀌어도 최초 승인 수명이 연장되는 것을 막습니다.

`tcp_mtls_rejections_total`은 수신 핸드셰이크, 워크로드 인가 및 승인 세대 실패를 셉니다. `tcp_mtls_lease_terminations_total`은 리스 기반 연결 종료를 셉니다. 둘 다 상태 메트릭과 Prometheus에 있습니다. 영구적인 행위자별 감사 기록이 아니며 인증서/개인 키 자료는 이 카운터에 노출되지 않습니다.

이는 게이트웨이 인증 TCP 경계를 규정합니다. HTTP 워크로드 주체 바인딩, 분산 신뢰/철회 전달, 영구 감사, 그리고 다른 경로로 클라이언트가 백엔드에 도달할 수 없다는 증명은 별도의 Zero Trust 요구 사항입니다.

## TCP 전송과 진단 워크로드

승인된 TCP 소켓과 공유 아웃바운드 TCP 연결은 요청/응답 프로토콜과 짧은 TLS 레코드에서 Nagle/지연 ACK 정체를 피하기 위해 `TCP_NODELAY`를 활성화합니다. 아웃바운드 설정은 같은 커넥터를 사용하는 SOCKS 프록시 연결, HTTP 사용자 정의 전송 및 프로브에도 적용되며 Unix 소켓은 영향받지 않습니다. 이로 인해 작은 패킷 빈도가 늘 수 있으므로 애플리케이션은 여전히 쓰기를 적절히 버퍼링해야 합니다.

소유한 루프백 워크로드에는 `cargo test --release --test tcp_mtls tcp_mtls_owned_echo_throughput -- --ignored --nocapture`를 실행하십시오. 최대 8개의 인증된 클라이언트가 평문 echo 백엔드를 통해 각각 8 MiB를 보내고 확인합니다. 시간은 TLS 핸드셰이크와 같은 크기의 응답을 포함하며 픽스처 생성/리스너 설정은 제외합니다. 픽스처도 TCP_NODELAY를 활성화합니다. 이는 진단 전송 측정이며 최대 연결 테스트나 상용 제품 비교가 아닙니다.
