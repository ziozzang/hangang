# 전용 상호 TLS를 사용하는 HTTP 워크로드 신원

[문서 목차](../README.ko.md) · [English](../HTTP_WORKLOAD_MTLS.md)

`Config.workload_http`는 TLS를 종료하고 클라이언트 인증서를 요구하는 전용 HTTP 리스너를 정의합니다. HTTP 경로는 `workload_auth`로 이 검증된 연결을 선택합니다. 경로는 `access_mode: "protected"`와 `resource_policy`를 선언해야 합니다. 이 리스너는 일반 공개 HTTP/HTTPS 및 ACME 리스너와 분리되어 있으므로 `workload_auth`를 활성화해도 공개 리스너가 mTLS가 되지 않습니다.

[예시](../../examples/http-workload-mtls.json)는 리스너 하나와 경로 하나를 보여 줍니다. 주소, 호스트 이름, 정규화된 절대 파일 경로는 예시일 뿐입니다. 인증서, 개인 키, 자격 증명 자료는 포함하지 않습니다. 활성 리스너는 해당 경로에서 유효한 로컬 자료가 검증될 때까지 사용할 수 없습니다. 성공 요청에는 도달 가능한 백엔드도 필요하며 백엔드 도달성은 시작 전제 조건이 아닙니다.

예시의 `GET /orders` 요청에서는 네 가지 검사가 중요합니다:

1. 클라이언트가 `client_ca_file`로 이어지는 인증서로 TLS를 완료하고 선택 `client_crl_file` 검증도 성공합니다. 리프에는 리스너 `tls.allowed_uri_sans`의 정확히 하나의 정규 SPIFFE URI SAN이 있습니다.
2. 선택 경로의 `workload_auth.listener_ids`에 실제 전용 리스너 ID가 있고 `allowed_uri_sans`에 검증된 URI가 있습니다.
3. 선택 경로는 Protected이고 강제 리소스 정책이 `principal.source: "workload"`를 식별합니다. 정확한 주체와 HTTP 메서드 허용 규칙이 검증 URI와 요청 메서드에 일치합니다.
4. 경로에 구성된 추가 Basic, JWT, 외부 인가도 모두 성공합니다. 이 검사는 조합되므로 유효 클라이언트 인증서가 이를 건너뛰지 않습니다.

참조 리스너가 없거나 비활성/제거/사용 불가이면 접근을 허용하지 않습니다. 일반 공개 리스너에 도달한 유효 인증서는 워크로드 근거를 만들 수 없고, 전용 리스너 클라이언트도 일치하는 `workload_auth` 없이는 업스트림 경로에 도달할 수 없습니다. 구성된 health 경로는 필수 TLS 클라이언트 검증 후 업스트림 라우팅 없이 준비 상태를 답할 수 있는 예외입니다. 사용 불가 리스너 참조를 경로에 유지해 안전하게 변경을 준비할 수 있으며 활성화 전까지 fail closed합니다. `resource_policy.enforce`가 명시적 `false`이면 주체/메서드 규칙은 실행하지 않지만 Protected 모드, 필수 정책 선언, 리스너 검증, 경로 로컬 워크로드 허용 목록은 계속 적용됩니다. 예시의 3단계 신원 검사에는 강제를 유지하십시오.

## 리스너와 신원 규칙

각 리스너에는 고유 ID, 0이 아닌 IP 소켓 주소, `enabled` 플래그(기본 `true`), [TCP 워크로드 mTLS](TCP_MTLS.md)와 같은 정책 모양의 `tls` 블록이 있습니다. 문서는 최대 64개 리스너를 허용합니다. TLS 정책은 서버 인증서, 개인 키, 클라이언트 CA 루트, 선택 CRL의 정규화된 절대 경로를 사용합니다. 활성 리스너는 게시 뒤 500ms마다 메타데이터, 5초마다 전체 내용을 검증합니다. 새 바인딩은 게시 후 자료 검증 성공까지 사용할 수 없습니다. 변경되거나 잘못된 클라이언트 CA/CRL은 이전 신뢰를 대체 수단으로 유지하지 않고 승인과 기존 인증 스트림을 닫습니다. 검증 교체는 새 세대를 만들며 비활성 리스너는 구조 검증만 유지하고 파일을 읽지 않아 손상 자료가 종료 편집을 방해하지 않습니다. 이는 로컬 자동 새로 고침이지 플릿 자료 배포가 아닙니다.

감시기는 전송 역할별 동일 정책을 그룹화하므로 여러 바인딩이 한 검사에서 같은 자료를 독립적으로 다시 열고 구문 분석하지 않습니다. 폴링 간격은 스케줄링 목표이며 파일 시스템 지연, 검사 크기, 스케줄러 부하가 관측 지연에 영향을 줍니다. 감독형 핸드오프 후 이전 프로세스가 연결을 배출하는 동안에도 검사가 계속됩니다. 로컬 새로 고침은 플릿 철회 순서나 CRL 롤백 방지를 강제하지 않습니다.

클라이언트 인증서는 필수 명시적 CA 검증을 쓰며 시스템 루트는 암묵 신뢰되지 않습니다. 리프에는 URI SAN이 정확히 하나 있어야 하고 URI는 구성 허용 목록 항목과 바이트 단위로 일치해야 합니다. SPIFFE ID는 소문자 trust domain을 가진 최대 2,048 ASCII 바이트이며 경로는 비어 있지 않은 슬래시 구분 세그먼트입니다. userinfo, 포트, 쿼리/프래그먼트, 퍼센트 이스케이프, 점 세그먼트, 모호한 끝 슬래시는 거부합니다. 이는 구성 서비스 신원을 검사할 뿐 개별 인간이나 SPIRE agent 존재를 확인하지 않습니다. 새 연결이 인증서 검사를 건너뛰지 못하도록 TLS 세션 재개, 티켓, early data를 비활성화합니다. CRL 구성 시 잘못됨, 만료, 알 수 없는 철회 상태는 거부하며 CRL이 없으면 자동 철회 조회/OCSP는 없습니다.

핸드셰이크 타임아웃은 기본 5,000ms, 허용 1–10,000ms입니다. fail-fast 프로세스 전체 핸드셰이크 게이트와 기존 연결 승인 제한이 동시 작업을 제한하며 거부 작업은 대기열에 넣지 않습니다. 리스너는 HTTP/1.1 또는 HTTP/2를 협상하고 인가 후 일반 스트리밍 응답과 SSE를 지원하며 HTTP/1.1 WebSocket 업그레이드를 지원합니다. WebSocket용 HTTP/2 extended CONNECT는 구현하지 않습니다. 이 소켓에서 비인증 HTTP 대체 수단을 노출하지 않습니다.

## HTTP 정책과 헤더 출처

`workload_auth.listener_ids`는 고유 ID 1–64개, `allowed_uri_sans`는 고유 정규 SPIFFE URI 1–128개입니다. 선택 `identity_header`는 검증 URI를 백엔드로 전달합니다. 이는 인증의 입력이 아니라 인증서 검증의 출력입니다. 게이트웨이는 경로 전반에서 구성 워크로드 신원 헤더 이름을 예약합니다. 클라이언트 헤더 조건과 다른 인증기는 이를 주장할 수 없고 클라이언트/Lua 쓰기는 수립된 값을 바꾸지 못합니다. 오리진은 이 헤더를 신뢰하기 전에도 직접 비신뢰 접근에서 격리해야 합니다.

전용 워크로드 리스너에서 소켓 피어는 직접 TLS 클라이언트입니다. 게이트웨이는 클라이언트 제공 전달 메타데이터를 제거하고 이 리스너에서 `X-Forwarded-For` 또는 신뢰 프록시 CIDR로 신뢰를 위임하지 않습니다. `Host`, `SNI`, 복사 헤더, 애플리케이션 제공 값은 워크로드 신원을 만들지 않습니다. 워크로드 mTLS와 함께 외부 인가 서비스를 구성할 수 있으며, 이 서비스는 피어 신원의 검증되지 않은 클라이언트 주장이 아니라 게이트웨이가 해결한 요청 컨텍스트를 받습니다.

보호 리소스 가드는 경로 우선순위와 일치 조건 전반에 계속 적용됩니다. 예시는 `resource_policy.principal.source: "workload"`를 사용합니다. 허용 규칙 주체는 최대 2,048 ASCII 바이트의 정확한 정규 SPIFFE URI이고 메서드는 정확한 대문자 이름 또는 명시적 `*`입니다. 강제 빈 허용 목록은 모든 요청을 거부합니다. 경로가 비활성화되어도 `workload_auth` 구성에는 리소스 정책이 필요합니다. 강제 리소스 범위 이동/제거는 [리소스 정책 전환 규칙](RESOURCE_POLICY.md)을 따릅니다.

## 게시, 연결 수명 및 핸드오프

리스너 등록은 Configuration 콘솔 또는 리비전 `If-Match`를 갖는 기존 전체 문서 `GET`/`PUT /v1/config`로 편집하며 별도 리스너 변경 API는 없습니다. 콘솔은 **Apply configuration**이 전체 후보를 게시할 때까지 JSON 문서에서 목록/생성/편집/활성화/제거를 단계화합니다. 기존 경로 API는 일반 리비전 검사 아래 `workload_auth`와 리소스 정책을 편집합니다. 구성 검증, bind, CAS 실패는 후보를 게시하지 않습니다. 게시 후 자료 검증이 보류될 수 있지만 성공할 때까지 바인딩은 닫힙니다. `GET /v1/status`는 활성 바인딩을 `workload_materials[{kind:"http",id,ready}]`로 보고하고 콘솔은 Configuration 표시 중 이 로컬 런타임 상태를 새로 고칩니다. `ready:false`는 인증 승인을 닫습니다. 미게시 초안 또는 사용 불가/오래된 상태는 ready로 표시하지 않습니다. 시작은 구성 워크로드 바인딩을 최대 10초 기다립니다. 이후 자료 실패가 전역 `/healthz`를 반드시 503으로 만들지는 않으므로 바인딩별 상태 또는 `hangang_workload_material_ready`/`hangang_workload_material_unavailable` 게이지를 확인하십시오.

활성 TCP 소켓을 한 번의 게시에서 워크로드 HTTP 리스너로, 또는 그 반대로 조용히 재해석할 수 없습니다. 먼저 이전 소켓 역할을 제거/비활성화하여 그 리비전을 게시한 뒤 새 역할을 추가하십시오. 활성 워크로드 리스너는 한 주소에서 활성 TCP 리스너와 겹칠 수 없고 공개 리스너도 별도 바인딩 주소가 필요합니다. 전용 리스너 제거/비활성화는 인증 연결을 닫습니다. 리스너 정책 또는 인증서/CA/CRL 자료 변경은 새 준비 세대를 만들지만 같은 자료/정책을 보존한 관련 없는 구성 변경은 이를 유지합니다.

요청 승인 시 경로는 검증 리스너 근거를 전체 경로 정책 세대에 바인딩합니다. **동일 워크로드 경로**의 편집(인증, 규칙, 범위, 다른 경로 필드 포함)은 기존 응답 스트림과 업그레이드 터널을 종료하며 관련 없는 경로 편집은 그렇지 않습니다. 리스너는 250ms 타이머로 인증서/CRL 만료와 준비 세대 철회를 검사하고 경로 응답 본문/WebSocket 터널도 경로 종료를 확인합니다. 이는 동작하는 스케줄러의 경계이지 즉시 네트워크 전체 철회 보장이 아니며 이미 전달된 바이트는 회수할 수 없습니다. 아직 유효 연결의 새 요청은 현재 스냅샷으로 평가됩니다. 경로가 JWT도 요구하면 토큰 만료, 서명 키 철회, 전체 경로 세대가 업로드/응답 스트림/터널의 활성 승인 조건으로 남습니다. [JWT 스트림 리스](JWT_AUTH.md)를 참조하십시오. JWT 또는 워크로드 신원 종료 중 하나가 요청을 끝낼 수 있습니다.

감독형 핸드오프는 형식화된 `WorkloadHttp` 리스너 descriptor를 사용합니다. 새 바이너리는 이 역할을 이해하지만 이전 바이너리는 이해하지 못합니다. [현재 버전 재시작 smoke test](../../tests/restart_smoke.py)는 워크로드 리스너 핸드오프와 잘못된 후보 복구를 실행합니다. 활성 워크로드 리스너 hot handoff에 의존하기 전에 supervisor/child 쌍을 업그레이드하고, 이전 바이너리 롤백을 안전하고 투명한 핸드오프로 설명하지 마십시오. 이 리스너는 플릿 전체 자료 배포나 게시 권한을 수립하지 않습니다.

`http_mtls_rejections_total`은 리스너 핸드셰이크/세대 승인 거부를, `http_mtls_lease_terminations_total`은 리스너 리스 종료를 셉니다. `workload_auth_rejections_total`은 경로 워크로드 인가 거부를, `workload_route_terminations_total`은 경로 스트림 철회를 셉니다. 이 상태/Prometheus 카운터에는 인증서 자료가 없고 영구 행위자 감사 기록이 아닙니다. 거부를 진단할 때 리스너와 경로 카운터를 모두 확인하십시오. 정확한 리소스 정책 주체/메서드 거부는 별도 정책 결과입니다.
