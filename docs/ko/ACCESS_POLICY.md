# 명시적 HTTP 접근 모드

[문서 목차](../README.ko.md) · [English](../ACCESS_POLICY.md)

`HttpRoute.access_mode`는 운영자가 의도한 인증 경계를 기록합니다. 게이트웨이는 비활성화된 경로를 포함해 어떤 경로나 전체 구성을 게시하기 전에 이를 검증합니다. 주체 수준의 인가에는 리소스 정책과 인증기를 사용하십시오.

| 값 | 의미 | 검증 |
|---|---|---|
| `legacy`(기본값, 출력 시 생략) | 기존 동작: 구성된 Basic/JWT/외부 인증은 계속 실행되며, 인증이 없어도 허용됩니다. | 새 인증기 요구 사항 없음. |
| `public` | 게이트웨이 Basic/JWT/외부 인증을 명시적으로 사용하지 않습니다. IP, 전송, Lua 및 애플리케이션 규칙은 여전히 요청을 거부할 수 있습니다. | `basic_auth`, `jwt_auth`, `auth`는 없어야 하거나 null이어야 합니다. |
| `application` | 인증을 업스트림 애플리케이션에 위임합니다. Hangang은 해당 애플리케이션의 로그인을 검증하지 않습니다. | `basic_auth`, `jwt_auth`, `auth`는 없어야 하거나 null이어야 합니다. |
| `protected` | 게이트웨이 인증이 필요합니다. | `basic_auth`, `jwt_auth`, `auth` 중 적어도 하나를 구성해야 합니다. JWT와 Basic은 함께 사용할 수 없으며, 구성된 모든 검사가 성공해야 합니다. Lua만으로는 이 요구 사항을 충족하지 않습니다. |

필드를 생략하면 기존 구성을 보존하고 새 로그인 요구 사항이 조용히 적용되는 일을 막습니다. 콘솔은 이 미지정 선언과 명시적 보호 모드를 구분합니다. 레거시 경로에도 동작하는 인증이 있을 수 있습니다. public/application 레이블은 소유 책임을 설명하며, 모든 요청의 성공을 증명하지는 않습니다.

주체/메서드 인가 및 대체 경로 섀도잉 방지는 [보호된 HTTP 리소스](RESOURCE_POLICY.md)를 참조하십시오. 아래 제한 사항은 `access_mode`만을 설명합니다.

네이티브 서명 액세스 토큰 구성과 그 제한은 [JWT 인증](JWT_AUTH.md)에 문서화되어 있습니다.

## 실수로 제거하는 것을 방지

예를 들어, 동작 중인 Basic 인증 경로에 `"access_mode": "protected"`를 추가합니다. 이제 다른 실제 인증기가 남아 있지 않으면 `basic_auth`만 제거하는 작업은 검증에 실패합니다. 실패한 API 쓰기는 활성 구성과 리비전을 변경하지 않습니다. 이 검사는 경로 편집기뿐 아니라 전체 구성 PUT 및 동적 로딩에서도 실행됩니다. UI에만 의존하는 보안 경계는 없습니다.

기존의 동일 ID 보호 경로에서 구성을 생략/기본 `legacy` 모드로 바꾸는 작업도 거부됩니다. 이는 오래된 편집기가 새 필드와 인증기를 모두 누락하는 일을 막습니다. 전환 검사는 활성 이전 스냅샷을 사용하며, 경로 삭제 후 재생성 또는 독립적으로 다시 작성된 파일을 새 프로세스가 로드하는 경우까지 지속되는 보안 권한은 아닙니다.

관리자는 소유 책임을 바꾸기 위해 명시적 `public` 또는 `application`을 설정하고 인증을 함께 제거할 수 있습니다. 이 기능은 중앙 인가, 불변 보안 정책 또는 이중 승인이 아닙니다. 경로 삭제, 다른 경로의 섀도잉, 안전하지 않은 경로 정규화 호환성 옵션 및 업스트림 직접 접근에는 더 폭넓은 리소스 정책/배포 제어도 필요합니다.

전용 HTTP 편집기는 접근 모드 선택기와 지역화된 설명을 제공하며, 보안 보기는 선언과 관찰된 구성 제어를 구분합니다. 기존 경로 CRUD와 전체 구성 API는 동일한 리비전/CAS 요구 사항으로 이 필드를 전달합니다. [OpenAPI](../openapi.json)에는 enum과 호환성 계약이 포함되어 있으며, 이 필드에 추가 엔드포인트는 필요하지 않습니다.

## 요청, 캐시 및 Lua

기존 Basic/JWT/외부 인증은 요청 경로에서 계속 실행됩니다. 보호된 경로는 공유 응답 캐시에서 명시적으로 제외됩니다. 일반 전달 경로에서 보호된 `Cache-Control: only-if-cached` 요청은 만족할 수 없는 캐시 전용 요청에 대해 504를 반환하기 전에 인증과 Lua 정책을 실행합니다. 인증되지 않은 요청은 대신 인증 거부/챌린지를 받습니다. 해당 캐시 전용 결과에는 업스트림 요청이 발행되지 않습니다. 신뢰된 외부 인증의 종결/전달 SSO 응답은 기존 동작을 유지하면서 의도적으로 더 일찍 끝날 수 있습니다. 전송 오류, 구문 분석, 경로 승인, IP 거부 및 TLS 리디렉션은 여전히 더 일찍 거부할 수 있으며, 이 모드는 잘못된 형식이거나 거부된 트래픽을 인증하겠다는 보장이 아닙니다.

일반 Lua 애플리케이션 헤더/본문/지원되는 백엔드 선택 변환은 계속 사용할 수 있습니다. 인증기가 소유하는 신원 필드는 값이 없어야 하는 신원 이름을 포함하여 일반 헤더 변경으로 덮어쓸 수 없습니다. Lua 스크립트를 단순히 구성하는 것은 검증된 주체가 존재한다는 증명이 아닙니다.

`protected`는 자동으로 전송 TLS를 요구하거나, JWT/OIDC를 검증하거나, 수신 클라이언트 인증서를 인증하거나, 기기 상태를 평가하거나, 사용자별 범위를 강제하거나, 이미 수립된 공개 스트림을 해제하거나, 영구 감사 기록을 만들지 않습니다. 현재 전송/인증기 제어를 명시적으로 구성하고 토폴로지를 검증하십시오. 특히 SNI 패스스루는 종료/인증된 신원 홉 없이 게이트웨이 검증 클라이언트 인증서를 수립할 수 없습니다.

## 업그레이드 호환성

이전 게이트웨이 바이너리는 `access_mode`를 이해하지 못하며 이를 포함한 구성을 거부할 수 있습니다. 공유 구성에 명시적 모드를 게시하기 전에 의도한 모든 리더를 업그레이드하십시오. 이런 문서가 저장된 후 기능 이전 바이너리로 롤백하는 것은 자동으로 호환되지 않습니다. 롤백 로드를 위해 보호를 조용히 제거하지 마십시오. 활성 스냅샷 전환 가드도 보호 선언을 생략한 이전 편집기의 대체를 의도적으로 거부합니다. 새 필드를 게시하기 전에 리더 버전을 조정하십시오.

## 예시

[examples/access-mode.json](../../examples/access-mode.json)은 외부 인증기 및 일반 Lua 헤더 변경과 함께 public, 애플리케이션 소유, protected 경로를 보여 줍니다. 사용하기 전에 예약된 예시 신원 엔드포인트와 루프백 백엔드를 소유한 서비스로 교체하십시오. 이 파일은 IdP를 설치하지 않습니다. TLS 종료/신뢰된 엣지 구성은 별도입니다.

## 검증

Rust 스위트는 기본/명시적 직렬화, 잘못된 모드, 보호된 인증기 제거, 이중 인증기, 비활성화된 경로, 상태/리비전 불변의 권위 있는 API 거부, 방어적 캐시 적격성 및 보호된 캐시 전용/인증/Lua 순서를 다룹니다. 브라우저 테스트는 모드 왕복, 편집기 검증 및 보안 분류를 실행합니다.

`python3 tests/access_mode_smoke.py`는 `HANGANG_BIN`(기본값: `target/debug/hangang`)을 사용하여 소유한 루프백 오리진과 실제 게이트웨이를 시작합니다. 레거시 동작, 실제 보호된 Basic+Lua 요청, 자격 증명 숨김, 캐시 전용 인증, 그리고 Lua 워커 슬롯 16개로 동시 클라이언트 12개에서 100개 작업(유효 요청, 거부 및 잘못된 정책 편집)을 확인합니다. 거부된 다운그레이드 10건은 활성 및 영속 리비전을 보존해야 하며, 인증되지 않은 요청은 오리진에 도달해서는 안 됩니다. 이는 동시성 정확성 테스트이며, **비교 성능 벤치마크가 아닙니다**. 픽스처는 임시 파일을 사용하고 프로덕션 엔드포인트를 사용하지 않습니다.
