# 보호된 HTTP 리소스

[문서 목차](../README.ko.md) · [English](../RESOURCE_POLICY.md)

HTTP 경로는 `resource_policy`로 게이트웨이 URL 네임스페이스를 인증된 주체 및 정확한 메서드 허용 목록에 바인딩할 수 있습니다. 이는 기존 `access_mode: protected` 인증 경계에 인가를 추가합니다. 네임스페이스는 경로의 호스트 매처와 `path_prefix`, `path_match`이며 경로 우선순위, 헤더/JSON 조건 또는 경로 활성화 여부에 의존하지 않습니다.

```json
{
  "id": "records",
  "hosts": ["app.example", "www.app.example"],
  "path_prefix": "/records",
  "path_match": "segment_prefix",
  "access_mode": "protected",
  "backends": ["http://127.0.0.1:8080"],
  "auth": {
    "url": "http://127.0.0.1:9080/check",
    "response_headers": ["x-authenticated-subject"]
  },
  "resource_policy": {
    "resource_id": "records",
    "principal": {
      "source": "external",
      "subject_header": "x-authenticated-subject"
    },
    "allow": [
      {"subjects": ["reader"], "methods": ["GET", "HEAD"]},
      {"subjects": ["editor"], "methods": ["GET", "HEAD", "POST", "PATCH"]}
    ]
  }
}
```

[전체 구성 예시](../../examples/resource-policy.json)는 TLS 강제 및 일반 Lua 애플리케이션 헤더 변경을 추가합니다.

예시에는 구성된 주소에서 실제 인가 서비스가 필요합니다. 신원 공급자를 설치하지 않습니다. 실제 토폴로지에 맞게 TLS와 신뢰된 프록시를 구성하십시오. 이 정책은 평문 인증 홉을 기밀로 만들지 않습니다.

## 주체와 동작

`principal.source: basic`은 구성된 네이티브 Basic 자격 증명 검증기가 반환한 사용자 이름을 사용합니다. `external`은 구성된 외부 인가 서비스의 성공 응답에서 복사한 정확히 하나의 비어 있지 않은 주체 헤더를 사용합니다. 헤더는 `auth.response_headers`에 나열되어야 하며 클라이언트 요청 헤더는 주체 근거가 될 수 없습니다. 누락, 반복, 쉼표 병합, 잘못된 형식 또는 과도한 외부 주체는 인가할 수 없습니다. `jwt`는 구성된 [네이티브 JWT 검증기](JWT_AUTH.md)의 서명된 `sub`를 사용하며 주체 헤더 필드는 없습니다. `workload`는 [전용 워크로드 mTLS 리스너](HTTP_WORKLOAD_MTLS.md)에서 검증된 클라이언트 인증서의 정확한 SPIFFE URI를 사용하며, 일반 공개 리스너의 요청은 이 근거를 제공할 수 없습니다. JWT와 Basic은 함께 사용할 수 없습니다. 구성된 모든 인증기가 성공해야 하며, 선언된 source가 평가할 주체를 선택합니다.

주체는 대소문자를 구분하는 정확한 문자열이며, 검증된 워크로드 SPIFFE URI 주체(최대 2,048 ASCII 바이트)를 제외하고 앞뒤 공백이나 제어 문자가 없는 최대 255 UTF-8 바이트입니다. 주체의 `*`는 문자 그대로의 이름입니다. 메서드는 정확한 대문자 이름(최대 32 ASCII 문자/숫자/하이픈)이며, 지원되는 모든 메서드 이름에는 명시적 `*` 규칙을 사용합니다. GET은 HEAD를 암묵적으로 부여하지 않습니다. 비어 있는 `allow` 배열은 모두를 거부합니다. 최대 32개 규칙, 규칙당 32개 주체와 16개 메서드, 총 512개 주체/메서드 항목 및 32 KiB 정책 텍스트를 허용합니다. 리소스 ID는 1–128개의 ASCII 문자/숫자 또는 `. _ - :`를 사용하며 외부 헤더 이름은 128바이트 제한입니다.

인가는 인증 후 Lua, 변환, 캐시 전용 완료 및 업스트림 승인 전에 실행됩니다. 일반 Lua 유연성은 계속 제공되지만 애플리케이션/신원 헤더를 바꿔도 이 결정에 이미 사용된 주체나 메서드는 바뀌지 않습니다. 보호된 경로는 공유 응답 캐시 대상이 아닙니다. 인증 챌린지와 비성공 SSO 리디렉션은 더 일찍 종료될 수 있습니다. 종결 성공 외부 인증 응답은 리소스 정책과 호환되지 않아 해제된 정책을 포함해 검증 중 거부됩니다.

## 네임스페이스와 라우팅

경로 선택 전에 게이트웨이는 요청 호스트와 정규 경로에 일치하는 모든 강제 리소스 네임스페이스를 검사합니다. 선택된 경로는 강제가 켜진 해당 리소스 ID를 가져야 합니다. 높은 우선순위의 공개 경로, 헤더/JSON 대안, 또는 공개 대체 경로가 있는 비활성 보호 경로는 가드를 우회할 수 없습니다. 다른 리소스 ID의 겹치는 네임스페이스는 요청을 거부합니다. ID를 공유하는 경로는 동일한 정책과 인증기를 선언해야 하므로 약한 대체 경로가 ID를 빌릴 수 없습니다. 같은 정책과 업스트림을 공유할 별칭은 `hosts`에 사용하십시오.

기존의 정확, glob, 컴파일된 regex 호스트 이름 매처는 라우팅과 가드 모두에 적용됩니다. 보호된 네임스페이스가 있는 호스트에서는 요청 Host, absolute-form authority 및 유효한 신뢰 프록시 호스트가 불일치하면 거부됩니다. 호스트 이름은 대소문자를 구분하지 않으며 포트는 별도 리소스 네임스페이스를 정의하지 않습니다. 보호된 호스트의 끝 루트 점 표기는 거부됩니다.

엄격하고 제한된 경로 프로필은 보호된 접두사 밖의 경로를 포함해 전체 보호 호스트에 적용됩니다. 경로는 2048바이트로 제한되고 가드 및 경로 일치를 위해 한 번 퍼센트 디코드되어 유효 UTF-8이어야 합니다. 인코딩 슬래시, 역슬래시, 퍼센트 기호(이중 디코딩), 쿼리/프래그먼트 구분자, 세미콜론 경로 매개변수, 제어 문자, 반복 슬래시 및 점 세그먼트는 거부됩니다. 레거시 `allow_dot_segments` 호환 설정이 켜져 있어도 이 제한이 적용됩니다. 구성된 리소스 경로 접두사는 이미 정규화되어 있어야 합니다. 쿼리는 네임스페이스나 동작 규칙의 일부가 아닙니다. 전달된 요청은 원래 경로 인코딩을 보존합니다.

이는 게이트웨이 URL 네임스페이스 계약이지 업스트림 객체의 모든 별칭을 발견하는 기능이 아닙니다. 관리자는 다른 비보호 호스트/경로 또는 구성된 재작성/기본 경로로 같은 백엔드를 노출할 수 있습니다. 업스트림별 Unicode 정규화(NFC/NFKC), 파일 시스템 별칭 및 백엔드 직접 접근은 이 가드로 조정되지 않습니다. 배포 전체에서 같은 해석을 사용하고 백엔드 자체의 객체 수준 인가를 강제하십시오. 일반 유효 UTF-8 경로 세그먼트는 지원하지만 Unicode 정규화 동등성은 주장하지 않습니다.

## 변경 및 명시적 해제

`enforce`는 기본적으로 true이며 true일 때 직렬화 출력에서 생략됩니다. 경로를 비활성화해도 가드는 유지됩니다. 활성 구성을 교체할 때 강제 네임스페이스를 생략, 삭제, 이동 또는 축소할 수 없습니다. 경로 ID가 바뀌어도 교체는 리소스 ID와 기존 호스트/경로 범위를 보존해야 합니다. 정확/glob 호스트 별칭은 기존 보호를 해제하지 않고 추가, 재정렬 또는 대소문자 정규화할 수 있습니다. 경로 모양과 regex 표현식은 동일하게 유지해야 하며, 서로 다른 glob/regex 표현식 간 포함 관계는 추정하지 않습니다.

네임스페이스를 의도적으로 해제하려면 먼저 기존 범위에서 `enforce: false`인 기존 정책을 게시하십시오. 그러면 네임스페이스와 주체/동작 강제가 즉시 해제되며 경로는 여전히 선언한 인증기를 요구합니다. 이후 리비전에서 정책이나 경로를 제거하거나 소유 책임을 명시적으로 변경할 수 있습니다. 같은 리소스 ID를 쓰는 모든 별칭은 일관되게 업데이트해야 합니다. 전용 영어/한국어 편집기는 정책, 규칙 및 명시적 해제/제거 단계를 제공하며 경로 CRUD와 전체 구성 PUT는 서버 검증 및 리비전 검사를 공유합니다.

전환 보호는 활성 스냅샷과 비교합니다. 독립적으로 재작성된 파일을 새 프로세스가 로드하는 경우까지 불변 중앙 권한은 아닙니다. 일반 경로에서 정책 게시가 이미 승인된 요청을 회수하거나 수립된 스트림을 닫지는 않습니다. 전용 워크로드 mTLS 경로에는 별도 경로 세대 리스가 있습니다. 해당 경로를 바꾸면 기존 응답 스트림과 업그레이드 터널이 종료되고, 리스너 만료 또는 철회도 연결을 닫을 수 있습니다. 이는 런타임 스케줄링으로 제한되며 이미 전달된 바이트를 회수할 수 없습니다. [네이티브 JWT 검증](JWT_AUTH.md)과 [전용 워크로드 mTLS](HTTP_WORKLOAD_MTLS.md)는 별도의 옵트인 인증 조각으로 구현됩니다. 기기 상태, 일반 철회, 영구 결정 감사 및 플릿 기능 강제는 이 리소스 가드 밖에 있습니다. 새 필드를 공유 구성에 게시하기 전에 모든 플릿 리더가 지원해야 하며, 이전 바이너리는 조용히 무시하지 않고 거부합니다.
