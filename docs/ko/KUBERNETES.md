# Kubernetes Ingress 컨트롤러

[문서 목차](../README.ko.md) · [English](../KUBERNETES.md)

Hangang은 `networking.k8s.io/v1` Ingress 및 Service 객체를 지속적으로 조정하여 실행 중인 프록시 설정에 반영할 수 있습니다. 각 프록시 복제본이 API를 독립적으로 읽으므로 경로의 가용성이 리더에 의존하지 않습니다. 이전의 `--import-ingress` 명령도 오프라인 변환용으로 계속 사용할 수 있습니다.

## 배포

이 저장소의 이미지를 빌드하고 게시한 뒤, `deploy/kubernetes/deployment.yaml`의 자리표시자 이미지를 교체하고, 비공개 관리자 토큰 파일을 만들어 kustomization을 적용합니다. 루트 [Dockerfile](../../Dockerfile)은 먼저 `make static`을 실행해야 하며 게이트웨이 바이너리만 패키징합니다.

```sh
umask 077
openssl rand -hex 32 > hangang-admin-token.private
kubectl create secret generic hangang-admin \
  --from-file=token=hangang-admin-token.private
kubectl apply -k deploy/kubernetes
```

`hangang-admin-token.private`를 저장소에 넣지 말고, 승인된 비밀 관리 시스템에 저장한 후 로컬 사본을 삭제하세요. 예시 Secret 매니페스트는 kustomization에 포함되지 않으며 자리표시자 값으로 적용해서는 안 됩니다. 제공된 `emptyDir`는 일회용이므로 Pod가 교체되면 관리자 계정, 세션, 로컬 감사 기록이 사라집니다. 이러한 기능을 사용하기 전에 Pod별로 적절히 보호된 영구 볼륨으로 교체하세요. 하나의 SQLite 계정 데이터베이스를 여러 복제본이 공유해서는 안 됩니다. 컨트롤러 Deployment는 Kubernetes API에서 경로를 가져오므로 경로 ConfigMap이 필요하지 않습니다.

제공된 Deployment는 자기 네임스페이스만 감시하고 `hangang` 클래스를 선택합니다. 네임스페이스 범위의 ServiceAccount, Role, RoleBinding을 사용합니다. Role에는 선택적인 TLS 모드를 위한 Secret 읽기 권한과 선택적인 주소 게시를 위한 `ingresses/status` 쓰기 권한이 포함됩니다. 이 기능을 사용하지 않는다면 해당 규칙을 제거하세요. 클러스터 전체를 다루는 컨트롤러는 `--kubernetes-namespace`를 생략하고 Role/RoleBinding을 의도적으로 검토한 ClusterRole/ClusterRoleBinding으로 교체해야 합니다. Deployment의 준비 상태 프로브는 공개 리스너에서 `--health-path /-/ready`에 HTTP 요청을 보내며, 이 복제본이 스냅샷을 게시했고 API 캐시가 여전히 최신이며 완전한지를 반영합니다([최신 상태와 준비 상태](#최신-상태와-준비-상태) 참조). 활성 상태 프로브는 소켓 검사로 유지됩니다. 따라서 API에서 분리된 복제본은 재시작되는 대신 Service의 트래픽 대상에서 제외됩니다.

컨트롤러는 기본적으로 투영된 서비스 계정 CA 및 토큰 경로를 사용합니다. 해당 CA로 API 서버를 검증하고, 리디렉션과 공개 신뢰 루트를 사용하지 않으며, 새 API 요청을 보낼 때마다 크기가 제한된 두 파일을 다시 읽습니다. 유효한 CA 교체는 HTTP 클라이언트를 원자적으로 교체합니다. 유효하지 않거나 일부만 투영된 자격 증명은 재시도를 유발하며 활성 경로 스냅샷을 교체하지 않습니다. Kubernetes는 [서비스 계정 관리](https://kubernetes.io/docs/reference/access-authn-authz/service-accounts-admin/#bound-service-account-token-volume-mechanism)에서 투영되고 순환 갱신되는 토큰 및 CA 볼륨을 설명합니다.

유용한 플래그는 다음과 같습니다.

- `--kubernetes-controller`: Kubernetes를 실행 중 설정의 유일한 소스로 사용합니다.
- `--kubernetes-namespace NAME`: 모든 목록 조회, 감시, Secret, 상태 쓰기를 하나의 네임스페이스로 제한합니다. 클러스터 전체 RBAC를 사용할 때만 생략하세요.
- `--ingress-class NAME`: `spec.ingressClassName`을 선택하며, 없으면 기존 어노테이션을 사용합니다. 기본값은 `hangang`입니다.
- `--kubernetes-api URL`, `--kubernetes-ca PATH`, `--kubernetes-token PATH`: 클러스터 내 검색과 자격 증명을 재정의합니다.
- `--kubernetes-tls`: 선택된 TLS Secret을 감시하고, 검증된 SNI 인증서 맵 하나를 경로 스냅샷과 함께 게시합니다.
- `--kubernetes-publish-address ADDRESS`: 허용된 모든 Ingress의 상태에 IP 주소 또는 호스트 이름 하나를 게시하고, 다른 복제본이나 컨트롤러가 쓴 항목과 병합합니다. 클라이언트가 실제로 연결하는 주소(복제본 집합 앞의 Service 또는 로드 밸런서)를 모든 복제본에서 동일하게 사용하세요. 복제본별 주소를 유지하지 않는 이유는 [여러 복제본 실행](#여러-복제본-실행)을 참조하세요.
- `--kubernetes-stale-seconds N`: 감시 대상 리소스 유형에 목록 조회, 감시 이벤트, 북마크 또는 감시 종료가 없는 상태를 얼마 동안 허용할지 지정합니다. 이 시간이 지나면 복제본은 준비되지 않은 것으로 보고합니다(기본값 60초, 30초의 감시 시간 제한보다 커야 함). 어느 경우든 복제본은 마지막 스냅샷을 계속 제공합니다.
- `--health-path PATH`: 공개 리스너의 인증 없는 준비 상태 엔드포인트입니다. 제공된 준비 상태 프로브는 `/-/ready`를 사용합니다. 첫 스냅샷 게시 전, 컨트롤러에 권위가 없을 때, 드레이닝 중에는 503을 반환합니다.

제공된 매니페스트에서 Secret 기반 TLS를 활성화하려면 다음을 실행합니다.

```sh
kubectl patch deployment hangang --type strategic \
  --patch-file deploy/kubernetes/tls-patch.yaml
```

선택된 Ingress의 각 TLS 항목은 `kubernetes.io/tls` Secret의 이름을 지정하고 하나 이상의 호스트를 나열해야 합니다. Hangang은 `tls.crt`와 `tls.key`를 base64 디코딩하고 PEM 인증서/키 쌍을 검증하며, 주장한 모든 호스트가 인증서 범위에 포함되는지 확인한 다음, 게시 전에 완전한 정확 일치/와일드카드 SNI 확인기를 구성합니다. `*.example.test` 같은 와일드카드 주장은 실제로 그 와일드카드 주체 대체 이름을 포함한 인증서가 필요합니다. 내부 검사 이름만 포함한 인증서는 거부됩니다. 인증서 발급과 갱신은 cert-manager 또는 다른 발급자의 책임입니다. 주장된 Secret이 삭제되거나 형식이 잘못되면 영향을 받는 각 Ingress와 인증서가 함께 철회되고 다른 Ingress는 계속 제공됩니다. Secret을 복구하면 경로도 복구됩니다. `kubernetes.io/tls` 유형의 Secret만 목록 조회 및 감시하므로(API 필드 선택자 `type=kubernetes.io/tls`), 네임스페이스의 관련 없는 Secret은 전송되지 않습니다.

## 호스트 이름 소유권

공유 컨트롤러는 인증서 유무와 관계없이 한 네임스페이스가 다른 네임스페이스의 호스트 이름으로 트래픽을 제공하게 해서는 안 됩니다. 선택된 각 Ingress는 `spec.rules[].host`, 각 `spec.tls[].hosts[]` 항목, 호스트 없는 HTTP 규칙 또는 `defaultBackend`에 대한 전체 포괄 패턴 `*`를 주장합니다. 호스트는 Kubernetes API가 이미 요구하는 대로 정확한 DNS 이름 또는 한 레이블 와일드카드(`*.example.test`)여야 합니다. 소유권은 현재 존재하는 객체만을 바탕으로, 어노테이션 없이 패턴과 네임스페이스별로 자동 결정됩니다.

- 패턴은 **이를 주장하는 가장 오래된 Ingress의 네임스페이스**에 속합니다. `metadata.creationTimestamp` 순으로 비교하고, 같은 초에 생성된 객체는 `metadata.uid` 순으로 비교합니다. 둘 다 API 서버에 기록된 사실이므로 목록 조회나 감시 순서와 관계없이 모든 복제본은 동일한 객체 집합에서 동일한 결론에 도달하며, 재시작한 복제본도 다른 복제본과 같은 결론에 도달합니다. 다른 네임스페이스의 해당 패턴 주장은 모두 거부됩니다. 주장한 Ingress 전체가 경합 중인 호스트를 명시한 경고와 함께 철회되고, 더 오래된 소유자가 밀려나거나 뒤로 재정렬되는 일은 없습니다.
- 소유 네임스페이스에서 선택된 Ingress 하나라도 그 패턴을 계속 주장하면 소유권이 유지됩니다. 해당 Ingress가 Secret 누락 등의 다른 이유로 일시 철회된 경우에도 마찬가지입니다. 소유 네임스페이스가 패턴 주장을 중단하면 다음 조정에서 남은 주장자 중 가장 오래된 쪽에 소유권을 부여합니다.
- 정확한 호스트와 이를 포함하는 와일드카드(`api.example.test`와 `*.example.test`)는 서로 다른 네임스페이스가 소유할 수 없습니다. 와일드카드 아래의 정확한 호스트를 다른 네임스페이스가 소유하고 그 소유자가 와일드카드의 가장 오래된 주장자보다 오래되었다면 와일드카드를 철회합니다. 그렇지 않으면 다른 네임스페이스의 더 최근 정확한 호스트를 철회합니다. 한 네임스페이스가 둘 다 소유할 수는 있습니다.
- Ingress를 삭제하고 다시 만들면 생성 시각이 갱신됩니다. 그 사이 다른 네임스페이스가 같은 호스트를 주장했다면 새 객체는 후발 주자가 되어 상대 객체가 제거될 때까지 철회된 상태로 남습니다. 따라서 네임스페이스를 서로 다른 팀이 관리하는 클러스터에서는 소유권 규칙에만 의존하지 말고 승인 단계에서 호스트 고유성을 강제해야 합니다(`spec.rules[].host`와 `spec.tls[].hosts[]`에 대한 검증 승인 정책). 컨트롤러의 규칙은 안전장치이지 접근 제어 시스템이 아닙니다.

소유권 결정과 변경은 로그에 기록됩니다. 철회된 Ingress의 네임스페이스, 이름, 잃은 호스트가 보고되고, 패턴이 이전되거나 해제될 때 관련 네임스페이스가 보고됩니다. 같은 네임스페이스 안에서는 여러 Ingress가 호스트를 공유할 수 있습니다(서로 다른 경로 또는 여러 객체가 재사용하는 인증서). TLS 주장에도 같은 규칙이 적용됩니다. 네임스페이스는 자신이 소유한 호스트에 대해서만 인증서를 주장할 수 있으며, 같은 네임스페이스의 다른 Ingress와 주장이 충돌하면 이름 순으로 나중 객체만 철회됩니다.

## 조정 동작

준비 상태에는 원하는 스냅샷의 활성화 성공도 필요합니다. 준비 또는 설정 적용에 실패하면 마지막 정상 경로는 유지되지만, 조정이 원하는 상태를 적용하거나 확인할 때까지 준비 상태는 철회됩니다. 새 감시 이벤트만으로는 이 실패가 해소되지 않습니다. 감독하에 인계할 때 쓰기 동결 상태에서도 컨트롤러 권위의 상실과 회복을 모두 추적합니다. 실패한 교체를 재개할 때 그 권위 상태가 보존되며, 종료를 위해 명시적으로 철회된 엔드포인트는 늦게 도착한 컨트롤러 확인으로 되살릴 수 없습니다.

초기 시작 시에는 게시 전에 Service와 Ingress를 목록 조회하고, TLS가 활성화되었다면 Secret도 조회합니다. 목록 조회는 일관된 페이지별 스냅샷을 사용하고 서버가 제공한 `continue` 토큰과 컬렉션 `resourceVersion`을 보존합니다. 기본 제한은 페이지당 객체 500개(Secret은 50개), 리소스 유형별 총 객체 10,000개, 응답당 8 MiB, 감시 이벤트당 4 MiB, 디코딩된 인증서 또는 키당 1 MiB입니다. Secret 목록은 API 서버의 감시 캐시가 `limit`을 무시하므로 저장소에서 제공받습니다. 그래도 응답 제한을 넘는 Secret 페이지는 페이지 크기를 절반으로 줄여 객체 한 개까지 다시 요청합니다. 따라서 크기가 큰 Secret 몇 개가 시작이나 재조회 작업을 막지 못합니다.

캐시된 객체에는 컨트롤러가 읽는 필드만 남깁니다. Secret에는 식별 정보, 유형, `tls.crt`, `tls.key`만 남고, Service에는 유형과 포트, Ingress에는 spec, 클래스 어노테이션, 로드 밸런서 상태가 남습니다. 관리 필드와 다른 어노테이션은 버립니다. 객체 수 외에도 보관하는 바이트 수를 리소스 유형당 64 MiB로 제한합니다. 어느 제한이든 초과한 목록 조회는 실패하고 마지막 정상 설정을 유지합니다. 제한을 초과하는 감시 `ADDED` 이벤트나 크기가 커진 `MODIFIED` 객체는 거부하고 캐시를 불완전한 것으로 표시한 뒤 재조회를 예약합니다. 재조회는 다음 삭제로 용량이 확보되면 즉시, 또는 최대 5초에 한 번, 또는 캐시가 추가 객체를 수용할 수 있을 때만 동작하는 60초 타이머에 따라 시작합니다. 불완전한 캐시의 내용은 계속 제공하지만 재조회가 성공하기 전까지 권위 있는 상태로 취급하지 않습니다.

독립적인 감시는 각 목록의 컬렉션 `resourceVersion`부터 시작합니다. 추가, 수정, 삭제된 객체는 완전한 캐시를 갱신하고, 북마크는 객체를 변경하지 않고 버전만 진행시킵니다. `410 Gone` 이벤트가 오면 [Kubernetes API 리소스 버전 의미 체계](https://kubernetes.io/docs/reference/using-api/api-concepts/#resource-versions)에 따라 캐시를 버리고 전체 목록을 다시 조회합니다. 전체 재조회는 원인이나 직전 결과에 관계없이 최소 5초 간격으로 시작하므로 `410`을 계속 받는 복제본도 매 구간에 최대 한 번만 목록을 조회합니다. 다른 API 오류는 200 ms에서 10초까지 제한된 지수 백오프로 다시 연결합니다. 서버가 열린 지 1초 이내에 닫은 감시도 즉시 다시 연결하는 대신 최대 5초까지 같은 백오프를 적용합니다. 재조회 간격, 재연결, 백오프, 상태 재시도의 모든 지연에 프로세스별 무작위 계수로 ±20 %의 지터를 적용하여, 같은 만료나 장애를 겪는 복제본들이 API 서버에 동시에 요청하지 않게 합니다. 감시 요청에는 서버 시간 제한 30초와 클라이언트 시간 제한 40초를 사용하여 토큰 및 CA 순환 갱신을 무한정 기다리지 않고 관찰합니다. 취소는 목록 조회, 감시, 재시도, 상태 대기를 중단하며 모든 감시자의 전송은 취소를 인지하므로, 조정이 느리고 내부 이벤트 큐가 가득 찬 경우에도 종료가 완료됩니다.

### 최신 상태와 준비 상태

컨트롤러는 감시 대상 리소스 유형마다 API 서버가 캐시를 마지막으로 확인한 시점을 기록합니다. 확인으로 간주하는 것은 완료된 목록 조회, 감시 이벤트, 북마크, 서버가 정상적으로 닫은 감시입니다. 목록 조회는 전체 재조회가 끝난 시점이 아니라 스냅샷의 `resourceVersion`이 정해진 시점(첫 페이지 응답)에 해당 유형을 확인합니다. 페이지별 목록의 후속 페이지도 같은 스냅샷에서 제공되므로, 느린 재조회에서 일찍 조회된 유형은 정확히 그 스냅샷만큼 오래된 상태입니다. 수락된 감시 요청 자체는 확인이 **아닙니다**. `200` 응답은 시작 버전이 아직 서버의 기록 안에 있다는 사실만 증명하며 이후 이벤트가 전달되었다는 뜻은 아닙니다. 따라서 최신 여부는 후속 이벤트, 북마크, 정상 종료로 판단합니다. 모든 필수 유형(Service, Ingress, `--kubernetes-tls` 설정 시 Secret)이 `--kubernetes-stale-seconds`(기본값 60초) 안에 확인되었고, 불완전한 캐시가 없으며, 스냅샷이 게시되었다면 복제본은 *권위 있는 상태*입니다. 한 유형이 그보다 오래 침묵하거나 용량 제한으로 객체를 거부한 뒤 복구 재조회가 아직 성공하지 못하면, 복제본은 로그에 이유를 남기고 준비되지 않은 것으로 보고합니다. 공개 `--health-path` 엔드포인트는 503을 반환하기 시작하여 로드 밸런서 또는 Service가 새 연결을 보내지 않게 합니다. 목록 조회나 스냅샷 생성이 진행 중일 때도 기한을 검사하므로, API 서버에서 멈춘 재조회는 요청이 반환되거나 시간 초과될 때까지 기다리지 않고 임계 시점에 준비 상태를 철회합니다. 이 경우에도 제공 중인 경로는 **철회하지 않습니다**. API에서 분리된 복제본은 여전히 도착하는 연결에 마지막 정상 스냅샷을 제공합니다. 그 사이 객체가 바뀌었는지와 관계없이 모든 유형이 다시 최신이며 완전해지면 즉시 준비 상태로 돌아옵니다. 유휴 감시는 서버가 닫을 때만 활성 상태를 입증하므로 임계값은 감시 시간 제한보다 커야 합니다.

Hangang은 런타임 설정 적용기를 호출하기 전에 후보 설정 전체를 검증합니다. API 실패, 잘못된 목록/감시 페이로드, 런타임 검증 실패가 발생하면 마지막으로 성공적으로 적용된 설정을 유지합니다. 목록의 일부 페이지만이나 불완전한 재조회 결과는 게시하지 않습니다. 선택된 Ingress는 개별적으로 격리됩니다. 지원되지 않는 필드, 누락된 Service, 소유하지 않은 호스트 이름, 누락되거나 유효하지 않은 TLS Secret은 해당 Ingress만 경고와 함께 철회하고 나머지는 게시합니다. 따라서 삭제된 인증서의 경로가 남아 있거나 한 테넌트의 실수로 다른 테넌트의 갱신이 멈추는 일이 없습니다.

생성된 설정은 경로 1,024개와 직렬화된 JSON 1 MiB로 제한됩니다. Ingress를 네임스페이스/이름 순으로 허용하면서 이 예산을 계산합니다. 어느 한도든 초과하게 만드는 객체는 단독으로 경고와 함께 철회하고 나머지 객체의 허용을 계속합니다. 따라서 전체 용량 제한이 삭제된 Secret의 철회나 관련 없는 갱신을 막지 않으며, 지나치게 큰 테넌트 객체는 용량 안에 들어올 때까지 제외됩니다.

Ingress 상태는 허용된 스냅샷에 들어간 Ingress에 대해서만 갱신됩니다. 이유를 불문하고 철회된 Ingress(소유하지 않은 호스트 이름, 누락되거나 유효하지 않은 Secret, 예산, 검증)는 주소를 받지 않으며, 이전에 상태에 이 컨트롤러의 주소가 남아 있다면 제거합니다. 철회 이유는 로그에 표시됩니다. 컨트롤러는 자신의 주소를 `status.loadBalancer.ingress`에 **병합**합니다. 현재 목록을 읽어 자신의 항목이 없으면 추가하고 자신이 쓰지 않은 항목은 제거하지 않습니다. 그러므로 서로 다른 `--kubernetes-publish-address` 값을 쓰는 복제본과 클래스를 공유하는 다른 컨트롤러도 모두의 주소가 들어 있는 목록으로 수렴합니다. 각 패치에는 관찰한 `metadata.resourceVersion`을 충돌 방지 사전 조건으로 넣습니다. `409 Conflict`는 객체별로 처리합니다. 컨트롤러는 해당 Ingress를 다시 읽고, 재조회된 객체가 결정의 대상과 여전히 동일하며(`metadata.uid`와 `metadata.generation`이 같고 여전히 해당 클래스에 선택됨), 새 목록에 병합합니다. 주소가 이미 있으면 건너뛰고, 아니면 새 `resourceVersion`으로 지터가 있는 백오프를 적용해 최대 세 번 재시도합니다. 그 사이 같은 이름으로 다른 객체가 다시 만들어졌거나, spec이 변경되었거나, 다른 클래스로 이동했다면 재조회된 객체에 대기 중인 갱신을 적용하지 않고 버립니다. 다음 조정에서 감시를 통해 본 새 객체를 다시 판단하므로, 허용되지 않은 Ingress에 주소가 게시되는 일은 없습니다. 상태 작업은 최대 네 개의 패치를 동시에 처리하는 백그라운드 큐에서 실행되며, 객체별로 합쳐 최신 원하는 상태가 우선합니다. 새 스냅샷의 게시는 상태 엔드포인트를 기다리지 않고, 상태 API가 멈추거나 실패해도 상태만 지연됩니다. 게시할 때마다 큐를 캐시와 대조합니다. 삭제되거나 클래스를 벗어났거나 이미 올바른 목록을 가진 Ingress의 작업은 버립니다. 따라서 큐에는 현재 선택된 Ingress당 최대 한 항목(객체의 중복본이 아니라 캐시에 있는 객체)이 남고, 상태 엔드포인트가 멈춘 동안 생성/삭제가 반복되어도 무한히 늘지 않습니다. 버린 작업 중 필요한 것은 다음 조정에서 캐시를 바탕으로 다시 계산합니다. 결과를 캐시에 반영하므로 관련 없는 이벤트가 패치를 반복시키지 않습니다. 이 플래그를 사용하지 않는다면 상태 권한은 불필요합니다. Kubernetes RBAC는 [인가 문서](https://kubernetes.io/docs/reference/access-authn-authz/authorization/)에 설명된 대로 기본적으로 거부합니다.

Ingress의 `Exact`, `Prefix`, `ImplementationSpecific` 경로는 각각 Hangang의 `exact`, `segment_prefix`, 원시 `prefix`에 대응합니다. 이름 또는 숫자로 지정한 TCP Service 포트를 지원하며 업스트림은 `SERVICE.NAMESPACE.svc:PORT`를 사용하고 엔드포인트 선택은 Kubernetes 네트워킹에 맡깁니다. 규칙은 Kubernetes의 호스트 선택 방식에 따라 결정적으로 정렬합니다. 정확한 호스트의 경로가 먼저, 한 레이블 와일드카드 호스트가 다음, 호스트 없는 규칙이 마지막입니다. 호스트의 구체성이 같으면 긴 경로, 정확한 경로 일치, 생성된 경로 ID 순으로 결정합니다. 따라서 와일드카드 또는 호스트 없는 규칙은 더 긴 경로에서 정확한 호스트로 들어온 요청을 가로챌 수 없습니다. Kubernetes 와일드카드 호스트는 앞의 DNS 레이블 하나와 일치합니다.

## 여러 복제본 실행

각 복제본은 API 서버를 상대로 자체 컨트롤러를 실행하고 자체 프록시에 게시합니다. 리더 선출도, 복제본 간 공유 상태도 없습니다. 이 설계에서는 복제본을 서로 바꿔 사용할 수 있습니다.

- 호스트 이름 소유권은 현재 객체의 순수 함수로 결정됩니다(가장 오래된 주장자가 승리). 따라서 서로 다른 이벤트 이력을 관찰했거나 다른 시점에 재시작한 복제본도 동일한 객체에 대해 동일한 경로를 게시합니다.
- 준비 상태는 복제본별입니다. 감시가 오래되었거나 캐시가 불완전한 복제본은 마지막 스냅샷을 계속 제공하면서 준비 상태 프로브에 의해 트래픽 분산 대상에서 빠지고 다른 복제본은 계속 동작합니다. `deploy/kubernetes/deployment.yaml`에서 `replicas`를 설정하고 `--health-path`에 대한 HTTP 준비 상태 프로브를 유지하세요. 단순 소켓 프로브는 오래된 복제본을 계속 트래픽 대상으로 알립니다.
- 상태 주소는 병합되므로 복제본들이 같은 주소나 서로 다른 주소를 게시해도 덮어쓰지 않습니다. 각 복제본은 설정된 자기 주소만 추가하고 제거합니다. **목록 뒤에 활성 상태 기록은 없고, 어떤 복제본도 다른 복제본의 항목을 제거하지 않습니다.** 따라서 축소되거나 충돌이 발생했거나 다른 `--kubernetes-publish-address`로 재시작한 복제본이 게시한 주소는 허용되었던 모든 Ingress의 `status.loadBalancer.ingress`에 무기한 남습니다. 그 상태를 사용하는 외부 DNS 컨트롤러, 서비스 검색, 대시보드 등도 이를 살아 있는 엔드포인트로 계속 취급합니다. 정상 종료 시에도 의도적으로 항목을 제거하지 않습니다. 롤링 업데이트나 감독하의 세대 교체는 같은 주소로 복제본을 재시작하며, 주소를 제거했다가 다시 추가하면 이유 없이 모든 상태 소비자에게 변동이 발생하기 때문입니다.
- 따라서 복제본들은 **하나의 공유 주소**를 사용하세요. 클라이언트가 실제로 연결하고 재시작, 재배치, 확장·축소 후에도 유효한, 복제본 집합 앞의 Service 또는 로드 밸런서의 IP 주소나 DNS 이름입니다. 그러면 목록에는 어느 단일 복제본도 소유하지 않는 엔드포인트 하나가 표시되며 로드 밸런서 자체가 변경될 때만 틀립니다. 복제본별 주소(복제본마다 노드 IP 또는 Pod IP)는 다른 시스템이 목록을 최신으로 유지할 때만 적합합니다. Hangang은 그렇게 하지 않습니다. Ingress별 하트비트 어노테이션도 이 용도로 검토했지만 채택하지 않았습니다. 상태 하위 리소스뿐 아니라 Ingress 메타데이터에 대한 쓰기 권한이 필요하고, 주기마다 복제본 및 Ingress별 쓰기 한 번과 클러스터의 모든 Ingress 감시자에게 감시 이벤트 하나를 발생시키며, 시계에 의존하고, 죽은 복제본의 항목과 동일한 주소를 합당하게 게시하는 다른 컨트롤러의 항목을 구별할 수 없기 때문입니다.
- 살아 있는 복제본이 더는 게시하지 않는 주소를 폐기하려면 상태 목록에서 한 번 제거하세요. 남은 복제본은 목록의 나머지 항목을 그대로 둡니다.

  ```sh
  RETIRED=192.0.2.7
  kubectl get ingress -A -o json \
    | jq -r --arg a "$RETIRED" '.items[] | select(.status.loadBalancer.ingress[]? | .ip == $a or .hostname == $a) | "\(.metadata.namespace) \(.metadata.name)"' \
    | while read -r ns name; do
        kubectl patch ingress -n "$ns" "$name" --subresource=status --type=merge -p "$(
          kubectl get ingress -n "$ns" "$name" -o json \
            | jq -c --arg a "$RETIRED" '{status:{loadBalancer:{ingress:[.status.loadBalancer.ingress[] | select(.ip != $a and .hostname != $a)]}}}'
        )"
      done
  ```

- 재조회 간격을 두고 모든 지연에 프로세스별 지터를 적용하므로, 같은 `410 Gone`이나 장애를 겪는 복제본 집합도 동시에 재조회하지 않습니다.

복제본들은 여전히 API 서버의 요청 속도 제한을 공유합니다. `N`개의 복제본은 시작 시 `N`번 목록 조회를 수행하고 리소스 유형마다 `N`개의 감시를 유지하며, 이는 독립 클라이언트 `N`개의 부하와 같습니다.

## 클러스터 없이 Ingress 어댑터 시험하기

[예시 Kubernetes List](../../examples/kubernetes/ingress-list.json)에는 Service 하나와 Ingress 하나가 들어 있습니다. 정확 일치 `/health` 경로, 경로 요소 접두사 `/` 경로, 클래스 선택, 이름이 지정된 Service 포트를 시험합니다. 저장소 루트에서 다음을 실행합니다.

```sh
cargo run --quiet --bin hangang -- --import-ingress examples/kubernetes/ingress-list.json --ingress-class hangang \
  | python3 -c 'import json,sys; d=json.load(sys.stdin); assert [r["path_match"] for r in d["http"]]==["exact","segment_prefix"]; assert all(r["backends"]==["http://api.demo.svc:8080"] for r in d["http"]); print("Ingress import: 2 ordered routes")'
```

이 명령은 변환만 검증합니다. 예시 Service에는 연결된 Pod가 없습니다. 아래의 [일회용 kind 검증](#검증)은 실행 중인 컨트롤러와 실제 백엔드를 시험합니다. 제공된 `deploy/kubernetes` 매니페스트도 프록시 컨트롤러와 공개 Service를 제공할 뿐, 애플리케이션 백엔드나 Ingress 객체는 제공하지 않습니다. 위와 같이 자리표시자 이미지를 교체하고 관리자 Secret을 만든 다음 실제 애플리케이션 Service와 Ingress를 제공하세요. 현재 컨트롤러는 IngressClass 객체를 읽지 않고 클래스 이름 문자열을 선택하므로 클러스터의 클래스 등록은 별도로 검토하세요. 현재 Gateway API 리소스는 조정하지 않습니다.

## 검증

모의 HTTPS API 테스트는 CA 검증 및 순환 갱신, 토큰 순환 갱신, 페이지 나누기, Secret SNI 자료, 삭제, 감시 재연결, `410 Gone`, 재조회 장애 시 기존 설정 유지, 상태 게시 조건, 취소를 다룹니다. 또한 더 오래된 소유자에 대한 네임스페이스 간 호스트 이름 주장, 이벤트 이력이 다른 두 복제본의 동일한 스냅샷 게시, 감시가 오래되면 준비 상태가 만료되고 API가 재개되면 복구되는 동작, 재조회 성공 전까지 불완전한 캐시의 준비 상태 해제, 두 복제본의 서로 다른 상태 주소 병합, 철회된 Ingress에서 주소가 제거되고 다시 게시되지 않는 동작, 상태 엔드포인트가 멈춘 동안의 게시, 반복되는 `410`에 대한 재조회 간격, 크기가 지나치게 큰 Secret 페이지, 용량 제한으로 거부된 객체의 복구, 감시자가 가득 찬 큐에서 대기하는 동안의 취소, 객체별 상태 충돌 재시도, 모든 패치가 멈춘 동안 생성/삭제가 반복되어도 제한된 상태 큐, 다른 클래스의 재생성된 객체를 충돌 시 재조회하고 패치하지 않고 버리는 동작, 재조회가 API 서버에서 멈춘 동안의 준비 상태 만료, 이미 임계값보다 오래된 유형의 스냅샷을 완료된 목록 조회가 새로 고치지 않는 동작, 수락되었지만 침묵하는 감시가 준비 상태를 복구하지 않는 동작도 다룹니다. 단위 테스트는 경로 순서, Ingress별 예산, 와일드카드 인증서 주장, 캐시 필드 제거와 바이트 제한, 가장 오래된 주장자의 소유권(시각, uid 동률 결정, 날짜 없는 객체, 이력 독립성), 정확 일치/와일드카드 소유권 중첩, 상태 목록 병합, 상태 큐 병합, 현재 캐시를 따르는 큐(삭제되거나 선택되지 않거나 이미 올바른 객체 제거, 객체 수 제한, 해제된 객체 미보관), 충돌 재조회의 uid/generation/class 일치 조건, 지터 범위를 다룹니다. 일회용 kind 검증은 고유한 클러스터, Docker 네트워크, 이미지, kubeconfig를 만들고 실제 TLS 경로, 상태 게시, Secret 순환 갱신/삭제, Ingress 삭제/재생성, 감독하의 SIGHUP 세대 교체를 검증한 뒤 자신이 만든 리소스만 제거합니다.

```sh
python3 tests/kubernetes_cluster.py
```
