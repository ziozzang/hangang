# 독립 품계 서버

[문서](../README.ko.md) · [English](../PUMGYE.md)

품계가 정책 저장·컴파일·CAS 게시·리비전·감사를 소유합니다. Hangang은 라우트의
서비스/메서드/등급 연결과 요청 집행을 맡고 고정된 도메인 위임으로 관리 화면을 제공합니다.


설정 최상위의 `pumgye_authority`를 사용하며 기존 내장 `pumgye` 정책과 동시에 둘 수
없습니다. 원격은 mTLS가 필수이고 로컬 평문은 loopback만 허용합니다. 예제는 합성 값이며
자격 증명 자체는 설정에 넣지 않습니다.

```json
{
  "decision_address": "192.0.2.10:9085",
  "management_address": "192.0.2.10:9084",
  "decision_token_env": "PUMGYE_DECISION_TOKEN",
  "admin_token_env": "PUMGYE_ADMIN_TOKEN",
  "tls": {
    "server_name": "pumgye.example.test",
    "ca": "/private/pumgye/ca.pem",
    "certificate": "/private/pumgye/gateway.pem",
    "key": "/private/pumgye/gateway.key"
  },
  "pool_size": 64,
  "timeout_ms": 100,
  "minimum_revision": 1
}
```

고정 endpoint의 서버 이름/CA를 검증하고 클라이언트 인증서를 제시한 뒤 판단 자격 증명을
검증합니다. 제한된 지속 PPG1 연결을 재사용하며 권한 1개 판단은 배치 할당을 생략하고
복수 권한은 최대 64개 요청의 상관을 검증합니다. 서비스 없음·guest·필수 네트워크 근거의
판단 불가/fail-open/observe·권한/등급/AAL 불일치는 허용하지 않습니다. 검증된 네이티브
호패 헤더와 신선한 Guard 근거를 사용하며 호출자 주장을 신뢰하지 않습니다. 보호된 경로는
응답/인증 캐시를 우회합니다.

500ms마다 네이티브 정책 probe를 수행하고 관측 리비전의 단조 증가와 authority 신선도
1초를 유지합니다. 품계 직접 게시도 리비전 변경·판단 불가/만료·Hangang 설정 퇴역에 따라
보호된 스트림을 종료합니다. 분산 멤버십·관측 watermark 영속화·authority incarnation
고정·전체 fleet의 호패 세션/Guard 스트림 회수는 아직 별도 구현 항목입니다.

품계 관리 화면은 Hangang 설정을 덮어쓰지 않고 소유 서버의 정책을 읽고 게시합니다.
다음 Hangang API는 실시간 관리자 권한이 필요하며 Viewer/익명은 거부합니다.

- `GET /v1/pumgye/policy`, `/v1/pumgye/status`, `/v1/pumgye/audit`.
- `PUT /v1/pumgye/policy`: `{revision, policy}` JSON, `If-Match`에 따옴표로 감싼
  품계 리비전, `X-Hangang-Config-Revision`에 조회가 반환한 Hangang 연결 설정 리비전.

두 범위 조건을 모두 확인합니다. 계정 회수와 직렬화해 요청을 승인하며 승인된 외부 게시 작업은
브라우저가 끊어져도 완료될 수 있습니다. 결과가 불확실하면 롤백을 추정하지 말고 다시 읽습니다.
응답 공개 전 실시간 역할·선택 authority를 재검증합니다. 경로·메서드·응답/본문 크기·동시성·
리다이렉트를 제한하며 클라이언트 URL·자격 증명·임의 헤더를 전달하지 않습니다. 판단 전용
노드에는 관리자 비밀값을 공급하지 않아도 되며 집행은 동작하고 관리는 차단됩니다. 품계는
검증된 전송 호출자를 감사에 기록하며 개인별 위임 감사는 후속 항목입니다.

기존 내장 정책은 이전 기준 구현입니다. 자동 역할/권한 부여나 DB/스키마 전환을 수행하지
않습니다. 라우트 활성화 전 소유 품계 서버에 이전 정책을 검증·게시해야 합니다.

라이브러리·기존 관리자/설정/리소스 테스트·OpenAPI 참조·브라우저 소유권/CAS/로그아웃과
실제 Hangang/품계 mTLS 프로세스를 소유한 HOP1/HGD1 peer로 검증합니다. 실제 호패/
수문장 원격 전송·혼합 인증·큰 정책 규모·전체 스택 100k HTTP QPS는 별도 통과 조건입니다.

## 서비스 신원

네이티브 호패 비인간 인증은 단일 `x-hopae-principal-kind: service` 또는
`x-hopae-principal-kind: workload`와
`x-hopae-aal: 0`·`s_`와 소문자 16진수 48자로 된 subject를 사용합니다. 인증된 `x-hopae-service-id`는 품계 게이트의 서비스 ID와 정확히 맞아야 합니다. 기존 사람
근거는 AAL 1–3을 유지하고 서비스 namespace는 사람 assurance로 바뀌지 않습니다.
미등록/중복/모순된 typed metadata는 거부합니다. 정규 workload AAL 0은 지원하고
network 단독 신원은 아직 지원하지 않습니다. 호패가 원천·게시/회수를 검증해야
하며 헤더는 인증된 네이티브 호패 응답에서만 받아들입니다.

라우트가 호패에 `authorization`을 보내고 `x-forwarded-user`·`x-hopae-aal`·
`x-hopae-principal-kind`를 받도록 설정합니다. 인증된 서비스에는 강제되는 품계
게이트·명시적인 서비스별 subject 역할·일치하는 메서드/정보등급/network 권한이
필요합니다. 역할이 `minimum_aal: 0`을 명시적으로 허용해야 하며 사람/MFA 요구는
만족하지 못합니다. API credential만으로 resource gate가 없는 기존 라우트까지
허용되지 않습니다. 서비스 인증의 terminal-response 모드로 권한 판단을 우회할
수 없습니다.

들어온 API Authorization credential은 네이티브 검증 후 소비하고 정책/변환 처리
전에 제거하며 upstream 전송 직전에 다시 제거합니다. application 자격 정보로
사용하지 않습니다. 서비스에 묶인 별도 변환과 스트리밍 credential 회수는 후속
작업입니다. 현재 회귀 검증은 소유한 네이티브 호패 프로토콜 peer와 실제 Hangang/품계
정책 평가를 사용합니다. 실제 여러 프로세스의 API 키 배포는 별도 검증 단계입니다.


## 네이티브 기계 인증 근거 만료

한강은 네이티브 서비스/워크로드 인증에 단조 시계 만료를 적용합니다. 호패의 선택
x-hopae-evidence-ttl-ms는 1~1000의 단일 십진 정수여야 하며 잘못된 값·중복·이미
소진된 기한은 거절합니다. 헤더 없는 기존 신뢰 peer에는 로컬 1초 한도를 적용합니다.
교환 전에 시계를 시작하여 통신 시간도 예산에 포함합니다. 클라이언트 헤더가 아닌
인증된 응답에서 제어 메타데이터를 읽습니다.

공통 라우트 lease는 응답 본문·진행 중 연산·upgrade·인증된 업로드 본문을 보호합니다.
정책과 원천이 그대로여도 인증 근거가 만료되면 idle 스트림을 닫습니다. 회수 검사는
현재 250ms 간격이므로 스케줄링 한도이며 정확히 1초의 전송 보장은 아닙니다.
수명보다 긴 기계 요청은 실패하거나 닫힐 수 있습니다. 갱신 없는 라우트는
만료에 닫힙니다. 선택형 재인증은 아래에 설명하며 개별 회수 구독·대규모 검증은
여전히 필요합니다. 기존
운영 게이트웨이 이미지에는 아직 이 동작을 배포하지 않았습니다.


## 선택형 네이티브 인증 근거 갱신

native 호패 전송이 있는 라우트에 auth.renew_native_evidence: true를 설정하면
유효한 장기 요청을 유지할 수 있습니다. 인증된 서비스/워크로드에만 적용하고
업그레이드된 peer의 명시적 TTL과 최소 100ms 남은 수명이 필요합니다. 기존 헤더
없는 peer는 갱신을 켤 수 없습니다. 원래 메서드·경로·클라이언트 문맥을 같은 제한된
인증 native 풀로 수명 중간 즈음 재검증합니다. 신원·종류·AAL·서비스가 정확히
유지되어야 합니다. 이를 위해 본문이나 원래 인증 정보를 앱에 전달하지 않습니다.

거절·원천 장애·용량 소진·신원 변경·잘못된 수명·만료는 해당 lease를 영구 회수합니다.
이전 만료 뒤 도착한 응답은 되살릴 수 없습니다. 품계·라우트·JWT·워크로드 회수도
독립적으로 적용합니다. bearer를 포함한 선택 인증 헤더는 요청 동안 프로세스의
사설 메모리에 유지하고 저장하거나 백엔드에 노출하지 않습니다. 마지막 참조가
닫히면 검증 태스크를 중단하고 문맥을 버립니다. 프로세스당 갱신 lease는 최대
4096개이고 native 풀 제한도 적용합니다. 결과 캐시는 없습니다.

기본값은 갱신 없는 만료입니다. 소유 native peer 테스트는 스트림을 2초 넘게 유지한
뒤 거절·검증기 장애·신원 변경·짧거나 만료된 근거를 검사합니다. 게이트웨이 갱신
메커니즘 검증이며 대규모 성능·실제 클러스터 watch 가용성 완료는 아닙니다.
Kubernetes 원천 polling은 수집 중 스트림을 독립적으로 회수할 수 있으므로 지속
가용성에는 남은 watch/follower 구현이 필요합니다.


갱신 수명주기 검증은 4096 슬롯 소진 시 거절, 마지막 참조 종료 시 실제 진행 중
native 소켓 취소, 전체 슬롯 반환, 응답 없는 timeout·비가역 만료도 확인합니다.
남은 수명 최소값은 갱신 응답에도 적용하고 짧은 TTL 테스트는 신원을 그대로 두어
신원 거절로 이 검사를 가리지 않습니다. 보관 헤더는 debug 표시에서 민감 값으로
표시합니다. 소유 전송/수명주기 테스트이며 대규모 포화 처리량 측정은 아닙니다.


## 요청 내부 네트워크 근거

입구의 인증된 Guard 판단이 유효하면 같은 요청의 품계 검사에서 사용할 수 있습니다.
Guard 인스턴스·canonical IP·관찰 정책 revision·원래 질의 시작 최대 1초 기한에
묶습니다. 만료나 binding 변경 시 필수 질의를 다시 합니다. snapshot·fail-open·
선택 cache hit는 재사용 근거를 만들지 않습니다. 요청 하나의 중복 RPC를 없애며
새 요청마다 정상 Guard 입구 검사를 거치고 공유 판단 캐시는 추가하지 않습니다.
진행 중 요청은 유효한 발급 네트워크 근거를 사용할 수 있으며 원격 정책 변경의
즉시 통지나 서명 permit receipt를 의미하지 않습니다.

## 선택 gRPC 판정 전송

`pumgye_authority.transport`를 `grpc`로 설정하고 `decision_address`를 품계의 gRPC
리스너로 지정합니다. 기본값은 `native`(PPG1)입니다. gRPC는 루프백에서도 설정된
mTLS 신원이 필수이며 관리는 별도 관리자 자격의 HTTPS를 계속 사용합니다.
고정한 품계 스키마 크레이트의 빌드에 protoc가 필요합니다.

HTTP/2 채널을 재사용하고 pool_size로 동시 처리를 제한하며 timeout_ms를 전체
판정 묶음에 적용합니다. 기본값·모순된 응답·캐시 힌트·오래된 리비전은 거부합니다.
리비전 하한은 단조 증가하고 묶음에 서로 다른 리비전이 있으면 거부합니다.
모든 권한이 허용돼야 통과합니다. 전송 실패·사용 불가·처리량 초과에 네이티브나
HTTP로 우회하지 않습니다. 리비전 감시도 선택된 전송을 사용합니다.
현재 묶음은 하나의 시간 제한 아래 개별 RPC를 전송합니다. 자격·인증서 교체와
채널 수명 검증은 운영 도입 전 별도로 필요합니다.

다음 명령으로 임시 DB의 실제 서버·클라이언트 연결을 검증합니다.

```sh
cargo build --example pumgye_grpc_qualification
python3 tools/pumgye_grpc_smoke.py --server /path/to/pumgye --client target/debug/examples/pumgye_grpc_qualification
```

전체 한강 요청 체인·K8s gRPC·운영 반영은 별도 검증 대상입니다.

## 네이티브 자원 카탈로그 (미릴리스)

고정한 품계 코어·계약 crate는 소유자가 관리하는 `resources`의 서비스·정보등급·
행위/권한 매핑·최소 AAL을 지원합니다. 타입이 있는 설정의 직렬화 왕복에서도
카탈로그를 유지하며 정책 컴파일에서 잘못된 관계를 거부합니다. 품계 콘솔은
카탈로그를 표시하고 기존 CAS 경로로 서비스/사용자/네트워크 변경을 게시할 때
이를 보존합니다. 항목 변경은 정책 JSON을 편집하며 원천 관리 정책은 읽기
전용입니다. 자원 RPC의 게이트웨이 집행 연결과 서명 permit은 아직 없으며
기존 서비스 게이트는 현재 동작을 유지합니다.

재사용 gRPC 클라이언트의 `decide_resource`는 네이티브 자원/행위/신원과 검증된
IP/AAL/수문장 근거를 받습니다. 기존 채널·용량·시간 제한·요청 ID·단조 리비전
경계를 공유합니다. 알려진 verdict/reason 조합과 TTL 0만 받아들이며 사용 불가·
오래되거나 모순된·알 수 없는 응답은 거부합니다. 소유한 두 프로세스 검사에서
기존 서비스 판정과 함께 자원 허용·최소 AAL 부족·관리자 자격/서버 이름 거부·
같은 채널에서 CAS 카탈로그 삭제·사용 불가 리비전 거부를 확인했습니다.
게이트웨이 라우트 선택과 실제 집행 적용은 남아 있습니다.

자원 질의에는 신뢰한 네이티브 `service_id`도 포함하며 권한 평가 전에 카탈로그 소속 서비스와 일치해야 합니다. 실제 소유자 서버 검사에서 다른 조건이 허용된 신원도 서비스 범위가 다르면 거부되는 것을 확인합니다.

## 자원 게이트 (미릴리스)

보호 라우트는 기존 `pumgye` 대신 `resource_policy.pumgye_resource`를 사용할 수 있습니다.

```json
{"service_id":"orders","resource":"db:orders","actions":{"GET":"select","POST":"update"}}
```

게이트는 하나만 선택하고 기존 `allow`는 비웁니다. 네이티브 호패 신원/AAL이
필수이며 기계 신원은 게이트의 네이티브 서비스 범위와 일치해야 합니다. 품계도
자원 소속을 검사합니다. 등급/권한은 게이트에서 보내지 않고 카탈로그가 정합니다.
매핑되지 않은 메서드와 알 수 없는 자원은 거부합니다. 독립 품계는 현재 필수
mTLS gRPC가 필요하며 새 게이트에 PPG1을 설정하면 설정 검사에서 거부합니다.
내장 품계는 같은 범위 코어 판정을 쓰고 로드할 때 카탈로그 행위를 검증합니다.
원격 허용은 기존 리비전/건강 lease에 연결해 라우트 회수·백엔드 전달·응답
스트리밍 경계를 유지합니다. 판정 캐시와 전송 fallback은 추가하지 않습니다.

로컬 실제 네 프로세스 mTLS gRPC 검사에서 자원 게이트와 기존 서비스 게이트가 통과했습니다. 자원 변형은 소유자 등급 변경·카탈로그 삭제/복구·메서드/서비스 분리·네트워크 차단/장애·거부 시 backend 호출 수 불변·호패/품계 재시작 후 영속 회수를 확인합니다. 자원 정책 7개·품계 7개·설정 36개 검사와 엄격한 all-target Clippy가 통과했습니다. 서명 릴리즈와 운영 반영은 남아 있으며 선택된 Kubernetes 검증은 아래에 기록합니다.

같은 정적 후보를 원격 Kubernetes 패키지에서 실제 Chromium과 검증했습니다.
자원 카탈로그 표시·소유자 등급/AAL/서비스 변경·카탈로그 삭제/복구·거부 시
backend 미전달·소유자 CAS·Pod 교체 후 인증/권한 영속 회수가 통과했습니다.
첫 실행은 응답 후 진단 backend 카운터 읽기 시간 초과였으며 이 멱등 조회만
제한된 전송 재시도를 허용합니다. 통과 실행에는 재시도가 없었고 보호 요청은
재실행하지 않습니다. 기존 노드/DNS/Ingress와 백업을 보존하고 전용 네임스페이스를
삭제했습니다. 후보 기능 검증이며 운영 반영이나 성능 근거는 아닙니다.

## 네이티브 인증 gRPC 클라이언트 (미릴리스)

pumgye_grpc_client::Client::decide_authenticated_resource는 기존 지속 mTLS
연결·공용 수용량·리비전 추적을 사용합니다. 신원·서비스·인증 수준은 불투명한
검증 호패 receipt에서만 가져오고 네이티브 질의는 자원/액션/IP·최종 요청 digest를
전달합니다. 호패 공용 protobuf 문맥을 품계와 공유하며 송수신 4 KiB/128바이트·
receipt 만료 이내 deadline을 적용합니다.

정확한 상관 ID·지원 Allow/Deny·캐시 TTL 0·안전한 정책/네트워크 리비전·단조
관측 하한을 확인합니다. 증명 검증 시각·단조 시작을 저장해 시계 역행/정지에도
유효 기간이 늘어나지 않습니다. 네이티브/HTTP 우회는 추가하지 않았습니다.
잘못된 응답·증명 시각 검사와 all-target Clippy를 통과했습니다. 실제 한강/품계
성공 RPC는 아래에서 검증했습니다. 게이트웨이 전달/설정은 후속 연결이며
운영 라우트나 서명 permit은 변경하지 않습니다.

의존성/클라이언트/증명 시각 변경 후 전체 all-target 검사 1,267개 통과·
명시적 제외 58개와 엄격한 Clippy를 통과했습니다. 소스/라이브러리 검증이며
운영 요청 전달 활성화는 아닙니다.

전용 authenticated_resource_qualification 예제는 실제 한강의 호패·품계
클라이언트로 지속 mTLS 연결을 사용해 세 판정 서버에 질의합니다. 품계의
tools/authenticated_resource_smoke.py --live-validation --grpc-decisions 검사에서
강제 자원 허용·네트워크 차단/해제·서명 신원 프로필 회수/복원·소유자 장애·
7종 신뢰 거부를 통과했습니다. 회수와 장애는 아직 만료되지 않은 이전 검증
receipt로 품계에 직접 재질의해 거부도 확인합니다. 로컬 디버그 프로세스
검증이며 정적 릴리즈·Kubernetes 반영·실제 게이트웨이 전달은 별도 검증입니다.
테스트 자격은 환경 변수 참조로만 전달합니다.

AuthorityRuntime::observe_authenticated_resource는 라우트 소유 ResourceGate·
메서드·IP·최종 digest·검증 서비스 receipt를 받습니다. 라우트/증명의 서비스
일치와 설정된 메서드/액션을 확인한 뒤 같은 품계 연결의 제한된 gRPC 채널과
리비전 하한을 사용합니다. 전용 예제로 이 연결 계층과 다른 서비스 증명·미등록
메서드·변경 digest 거부를 검증했습니다. 관측 결과만 반환하며 기존 권한 lease의
상태 감시를 시작하거나 갱신하지 않습니다. 라우트 활성화 전 최종 요청 변환·
증명 소유자/라우트 최신성·upstream 전달 연결이 필요합니다.

hopae_native::Client::validate_service_receipt는 검증된 서비스 receipt만 사용해
기존 mTLS 채널로 호패 원천에 재질의합니다. 발급과 호출자 인증·수용량을
공유하며 송수신 2 KiB/64바이트·1초와 원래 증명 만료 이내 deadline을 적용합니다.
정확한 요청 ID·원래 만료 시각 일치를 요구하고 로컬 벽시계/단조 시간·관측한
프로필 리비전 하한을 검사합니다. 결과는 최신 원천 관측이며 권한 lease나
permit이 아닙니다. 실제 세 서버 검사에서 한강 클라이언트가 현재 증명을
허용하고 만료 전 회수/장애 증명을 거부함을 추가 확인합니다. 이어 품계에
질의하기 직전에도 이전 증명이 유효함을 확인하므로 만료를 원격 수명주기
거부의 근거로 대체하지 않습니다.

projection_binding::digest_upstream은 선택된 HTTP(S) upstream URI의 정확한
경로/쿼리와 완성된 최종 본문을 바인딩합니다. 실제 게이트웨이 URI 합성
검사에 backend 기본 경로·재작성 경로·중복/인코딩 쿼리·host override를
포함했습니다. 합성 이전 경로나 빈 대체 본문은 다른 digest가 됩니다. 이
어댑터는 origin-only target·미지원 scheme·userinfo authority·모호하거나 잘못된
경로를 거부합니다. 정규 요청 digest에는 URI authority가 없으므로 서비스/
audience와 backend 소유자 바인딩은 별도 요구입니다. 이 함수는 스트림 버퍼링·
증명 발급·전달을 활성화하지 않습니다.

projection_entity::prepare는 소유자가 제공한 공용 수용량·본문 크기 제한
(1바이트–16 MiB)·시간 제한(최대 5초) 안에서 최종 본문 전체를 보존합니다.
처리 슬롯은 준비된 요청과 전달 본문에 유지합니다. 단일 프레임은 원래 Bytes
버퍼를 재사용하며 분할된 본문은 원천 프레임 버퍼 외에 필요한 용량을 2의 거듭제곱
단위로 늘리되 설정 상한을 넘지 않습니다. 할당 실패도 거부합니다. 64프레임마다 실행을 양보해 연속 빈 프레임도 deadline/취소를
막지 않습니다. 수용량·모호하거나 불일치하는 길이·크기 초과·본문 오류·미지원
트레일러·잘못된 최종 target은 거부합니다. 전달 프레이밍은 보존된 바이트에서
다시 생성하며 이 단계가 권한을 부여하지는 않습니다.

바이트 보존·슬롯 수명/취소·버퍼 재사용·잘못된 입력을 검사하는 10개 테스트를
통과했습니다. 실제 한강 세 서버 검사도 준비된 최종 요청의 digest를 사용하며
빈 본문과 --nonempty-entity 모두 허용·네트워크/인증 수명주기·장애·신뢰 거부를
통과했습니다. 품계 자체 클라이언트도 비어 있지 않은 본문 검사를 통과했습니다.
로컬 본문 준비/판정 검사이며 실제 게이트웨이 변환이나 upstream 전달·정적
릴리즈·Kubernetes·운영 반영 검증은 아닙니다.

예약 검사에서 16 MiB 제한에서도 13바이트 분할 본문의 벡터 용량은 16바이트이며,
2의 거듭제곱이 아닌 상한 아래에서 기하급수적 증가·크기/오버플로 거부 시 추가
할당 없음을 확인했습니다. 전용 --nonempty-entity --fragmented-entity 모드는
발급 전 실제 데이터 프레임 두 개를 한강 본문 준비 경로에 넣으며 세 서버의
허용/수명주기/장애/신뢰 검사를 통과했습니다. 선택한 클라이언트가 준비 프레임
두 개를 보고해야 하며 이를 지원하지 않는 클라이언트는 테스트가 거부합니다.
기본 빈 본문과 품계의 단일 본문 호환 검사도 통과했습니다. 로컬 기능·용량
검사이며 전체 게이트웨이 처리량 검증은 아닙니다.

미릴리스 native_resource::Binding은 불변 자원 게이트·서비스/audience 범위·
발급자 pin을 한 번 컴파일합니다. prepare_scoped는 요청마다 문자열을 복사하지
않고 그 범위를 재사용합니다. 준비된 요청은 정확한 범위 객체를 보관하며 다른
설정 객체는 값이 동일해도 거부합니다. 서비스 증명의 범위·digest도 준비된
요청 자체에서 가져옵니다.

Binding::observe는 실제 증명 발급·인증된 품계 자원 조회·허용 결과의 호패
재검증을 연결합니다. 허용 관측 반환 전 증명 만료와 같은 클라이언트의 로컬
관측 정책/네트워크 리비전 하한을 확인하며 기존 권한 상태 lease를 갱신하지
않습니다. 실제 세 서버 검사도 이 단계를 사용해 빈 본문·분할된 비어 있지 않은
본문의 수명주기/신뢰 검사를 통과했습니다. 본문 검사 10개와 gRPC 응답/리비전
검사 4개를 통과했습니다. 로컬 하한은 반환 후 원격 최신성을 증명하지 않습니다.
결과는 관측이며 실제 게이트웨이 설정/라우트 fence·upstream 효과·서명 permit/
변환·릴리즈·운영 반영은 후속 작업입니다.
