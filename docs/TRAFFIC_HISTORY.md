# Recent traffic metadata

Hangang keeps a process-local ring of completed HTTP **response-head** records for the administrator console. It retains at most 4096 records and exposes only records younger than 60 seconds. The capacity can shorten the visible window: approximately 100 requests/second fills it in 41 seconds; 1000 requests/second fills it in about 4 seconds. Old entries are pruned on the next insert or snapshot, so an idle process may physically hold stale bounded entries until then, but the API never returns them after expiry. The ring is not a durable access log or a packet capture.

Each record contains a timestamp, actual socket peer IP and source port, effective client IP, HTTP method, path without query string, matched route ID when one was selected, response status, time to response headers, protocol and TLS flag. The effective client IP uses forwarding headers only when the socket peer matches configured trusted proxy CIDRs; otherwise it equals the socket peer. A matched route ID can appear on a request later denied by TLS, IP, authentication or policy checks. Response-head time does not include streaming body or upgraded tunnel lifetime. Health probes are excluded; rejected data-plane requests are included. Strings are bounded and nonprintable bytes are replaced. Headers, authorization values, cookies, request and response bodies, and query strings are never copied into this ring. A secret embedded in a **path segment** can still appear in the administrator-only path field, so applications should not put credentials in URL paths.

Only administrator accounts and the system administrator token may read `GET /v1/traffic` or receive `event: traffic` on `/v1/events`; viewer sessions receive status events without client IP history. History reads accept an optional `after` cursor and `limit` up to 128. The response includes `gap` when records between the cursor and current ring were evicted or the cursor belongs to a different generation, `dropped_total` counts age and capacity evictions, and `server_time_unix_ms` lets the browser calculate remaining retention without trusting its wall clock. The SSE stream sends at most 128 records per roughly one-second tick, so sustained rates above 128 requests/second can produce a gap even while the ring holds newer records. Dashboard rate charts should use aggregate status counters; recent request records describe activity, not a complete high-volume audit trail.

Raw TCP connections use a separate bounded [active/recent connection history](TCP_CONNECTION_HISTORY.md), with lifecycle outcomes and application byte counts.

The revisioned [HTTP recording policy](HTTP_RECORDING.md) can deliberately omit selected response heads from this ring and enabled access tracing. Rows carry the decision's configuration `policy_revision`; batches expose cumulative `filtered_total` independently of eviction counts. Empty SSE traffic frames update these counters even when every new event is omitted. This selective history must not be treated as complete auditing.
