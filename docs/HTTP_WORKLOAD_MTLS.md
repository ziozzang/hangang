# HTTP workload identity with dedicated mutual TLS

`Config.workload_http` defines dedicated HTTP listeners that terminate TLS and require a client certificate. An HTTP route opts into that verified connection with `workload_auth`. The route must declare `access_mode: "protected"` and have a `resource_policy`. This listener is separate from the ordinary public HTTP/HTTPS and ACME listeners; enabling `workload_auth` does not turn a public listener into mTLS.

[The example](../examples/http-workload-mtls.json) shows one listener and one route. Its addresses, hostname, and normalized absolute file paths are illustrative. It contains no certificate, private key, or credential material. The enabled listener remains unavailable until valid local material is verified at those paths. Serving a successful request also requires a reachable backend; backend reachability is not a startup prerequisite.

For the example's `GET /orders` request, four checks matter:

1. The client completes TLS with a certificate chaining to `client_ca_file`; optional `client_crl_file` verification also succeeds. The leaf has exactly one canonical SPIFFE URI SAN in the listener's `tls.allowed_uri_sans`.
2. The selected route's `workload_auth.listener_ids` contains the actual dedicated listener ID, and its `allowed_uri_sans` contains the verified URI.
3. The selected route is Protected and its enforced resource policy identifies `principal.source: "workload"`. Its exact subject and HTTP method allow rule matches the verified URI and request method.
4. Any additional Basic, JWT, or external authorization configured on the route also succeeds. Those checks compose; a valid client certificate does not skip them.

An absent, disabled, removed, or unavailable referenced listener grants no access. A valid certificate reaching an ordinary public listener cannot construct workload evidence, and a client on the dedicated listener cannot reach an upstream route without a matching `workload_auth`. The configured health path is an exception: after mandatory TLS client verification it can answer readiness without routing upstream. A configured but unavailable listener reference may remain in a route to stage changes safely; it fails closed until the listener is active. If `resource_policy.enforce` is explicitly `false`, its subject/method allow rules do not run, although Protected mode, the required policy declaration, listener verification, and route-local workload allowlists still apply. Leave enforcement enabled for the three-level identity check in the example.

## Listener and identity rules

Each listener has a unique ID, a nonzero IP socket address, an `enabled` flag (default `true`), and a `tls` block using the same policy shape as [TCP workload mTLS](TCP_MTLS.md). The document admits at most 64 listeners. The TLS policy uses normalized absolute paths to a server certificate, private key, client CA roots, and optional CRLs. Enabled listeners watch these local files after publication: metadata is polled every 500 ms and complete contents are verified every 5 s. A newly published binding remains unavailable until post-publication material verification succeeds. A changed or invalid client CA or CRL closes admission and existing authenticated streams rather than keeping old trust as a fallback. A verified replacement creates a fresh generation. A disabled listener retains structural validation but does not read those files, so damaged material does not obstruct a shutdown edit. This is local automatic refresh, not fleet material distribution.

The watcher groups identical policies by transport role, so multiple bindings do not reopen and parse the same material independently during a sweep. These polling intervals are scheduling targets; filesystem latency, sweep size and scheduler load affect the observation delay. Material checks continue while an old process drains established workload connections after a supervised handoff. Local file refresh does not enforce fleet-wide revocation ordering or CRL rollback prevention.

Client certificates use mandatory explicit CA verification; system roots are not implicitly trusted. The leaf must have exactly one URI SAN, and its URI must match a configured allowlist entry byte for byte. SPIFFE IDs are ASCII, at most 2,048 bytes, with a lowercase trust domain; any path uses nonempty slash-separated segments. Userinfo, ports, query/fragment, percent escapes, dot segments, and ambiguous trailing slashes are rejected. This checks a configured service identity, not the identity of an individual human or the presence of a SPIRE agent. TLS session resumption, tickets, and early data are disabled so a new connection cannot skip the certificate check. If CRLs are configured, invalid, expired, or unknown revocation status is rejected; without CRLs there is no automatic revocation lookup or OCSP.

The handshake timeout defaults to 5,000 ms and accepts 1–10,000 ms. A fail-fast process-wide handshake gate and existing connection admission limits bound concurrent work; rejected work is not queued. The listener negotiates HTTP/1.1 or HTTP/2 and supports ordinary streaming responses and SSE after authorization; HTTP/1.1 WebSocket upgrades are supported. HTTP/2 extended CONNECT for WebSockets is not implemented. It does not expose an unauthenticated HTTP fallback on that socket.

## HTTP policy and header provenance

`workload_auth.listener_ids` has 1–64 distinct IDs; `allowed_uri_sans` has 1–128 distinct canonical SPIFFE URIs. The optional `identity_header` forwards the verified URI to the backend. It is an output of certificate verification, **not** an input to authentication. The gateway reserves configured workload identity header names across routes: client header predicates and other authenticators cannot claim them, and client or Lua writes cannot replace the established value. An origin should still be isolated from direct untrusted access before treating that header as trustworthy.

On a dedicated workload listener, the socket peer is the direct TLS client. The gateway strips client-supplied forwarding metadata and does not delegate trust through `X-Forwarded-For` or a configured trusted-proxy CIDR on that listener. `Host`, `SNI`, copied headers, and application-supplied values do not create workload identity. An external authorization service can be configured in addition to workload mTLS; it receives the gateway's resolved request context, not an unverified client assertion of peer identity.

Protected resource guards still apply across route priority and matching predicates. The example uses `resource_policy.principal.source: "workload"`; its allow-rule subjects are exact canonical SPIFFE URIs up to 2,048 ASCII bytes, and methods are exact uppercase names or an explicit `*`. An empty enforced allowlist denies every request. The gateway requires a resource policy even when a route's `workload_auth` is configured on a disabled route. Moving or removing an enforced resource scope follows the [resource-policy transition rules](RESOURCE_POLICY.md).

## Publication, connection lifetime, and handoff

Listener registration is edited through the Configuration console or the existing full-document `GET`/`PUT /v1/config` with revision `If-Match`; there is no separate listener mutation API. The console stages list/create/edit/activation/removal in the JSON document until **Apply configuration** publishes the whole candidate. Existing route APIs edit `workload_auth` and resource policy under their usual revision checks. A failed configuration validation, bind, or CAS does not publish the candidate. Material verification may be pending after publication, but the binding remains closed until it succeeds. `GET /v1/status` reports enabled bindings as `workload_materials[{kind:"http",id,ready}]`; the console refreshes this local runtime state while Configuration is visible. `ready:false` closes authenticated admission. An unpublished draft or unavailable/stale status is never presented as ready. Startup waits up to 10 s for configured workload bindings. A subsequent material failure need not make global `/healthz` return 503: other listeners can remain ready, so inspect per-binding status or the `hangang_workload_material_ready`/`hangang_workload_material_unavailable` gauges.

An active TCP socket cannot be silently reinterpreted as a workload HTTP listener, or the reverse, in one publication. First remove or disable the old socket role and publish that revision, then add the new role. Enabled workload listeners cannot overlap enabled TCP listeners on one address. Public listeners must also have separate binding addresses. Removing or disabling a dedicated listener closes its authenticated connections. A changed listener policy or certificate/CA/CRL material creates a new prepared generation; unrelated configuration changes that keep the same material and policy preserve it.

At request admission the route binds its verified listener evidence to the full route policy generation. An edit to **that same workload route** (including its auth, rules, scope, or other route fields) retires its existing response streams and upgraded tunnels; an unrelated route edit does not. The listener checks certificate/CRL expiry and prepared-generation withdrawal on a 250 ms timer, while route response bodies and WebSocket tunnels also check route retirement. This is a bound under a running scheduler, not an instantaneous network-wide revocation guarantee. Bytes already delivered cannot be recalled. A new request on a still-valid connection is evaluated against the current snapshot. When the route also requires JWT, its token expiry, signing-key withdrawal and full route generation remain live admission conditions for uploads, response streams and tunnels; see [JWT stream leases](JWT_AUTH.md). Either JWT or workload identity retirement can end the request.

Supervised handoff uses a typed `WorkloadHttp` listener descriptor. A new binary understands that role; older binaries do not. [The current-version restart smoke test](../tests/restart_smoke.py) exercises handoff with a workload listener and recovery from a bad candidate. Upgrade the supervisor/child pair before relying on hot handoff with an active workload listener, and do not describe an old-binary rollback as a safe transparent handoff. This listener does not establish fleet-wide material distribution or publication authority.

`http_mtls_rejections_total` counts listener handshake/generation admission rejection and `http_mtls_lease_terminations_total` counts listener lease termination. `workload_auth_rejections_total` counts route workload authorization denials and `workload_route_terminations_total` counts route-stream withdrawal. These status/Prometheus counters contain no certificate material and are not durable actor audit records. Inspect both listener and route counters when diagnosing a denial; an exact resource-policy subject/method denial is a separate policy result.

Implementation boundaries are in [configuration validation and snapshot preparation](../src/config.rs), [the dedicated listener](../src/workload_http.rs), [route authorization](../src/workload_auth.rs), [HTTP admission and stream fencing](../src/proxy.rs), and [the typed handoff protocol](../src/restart.rs).

## 한국어 요약

`workload_http`는 일반 공개 HTTP/HTTPS와 별도인 클라이언트 인증서 필수 수신기를 만든다. 보호된 HTTP 경로는 `workload_auth`로 실제 수신기 ID와 정확한 SPIFFE URI를 허용하고, 적용 중인 `resource_policy`에서 주체와 메서드를 다시 검사한다. 인증서가 유효하더라도 세 허용 목록 중 하나라도 불일치하면 통과하지 못한다. 활성 수신기의 로컬 파일은 메타데이터를 500ms마다, 전체 내용을 5초마다 재확인한다. 새 바인딩은 게시 후 검증될 때까지 대기하며 잘못된 클라이언트 CA·CRL은 해당 수신기의 인증 연결과 기존 스트림을 닫는다. 현재 인스턴스 상태는 `GET /v1/status`와 구성 화면에서 확인한다. 이 기능만으로 플릿 전체 자료 배포, 영구 감사, 백엔드 직접 접근 차단까지 완성되지는 않는다.
